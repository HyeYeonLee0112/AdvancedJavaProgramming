## 01. Maven 프로젝트로 바꾸고 창 띄우기 — #33

### 01-1. Java 버전과 Eclipse 프로젝트 확인

PowerShell에서 다음을 실행한다.

```powershell
& 'C:\Users\이혜연\.jdks\temurin-21\bin\java.exe' --version
& 'C:\Users\이혜연\.jdks\temurin-21\bin\javac.exe' --version
```

둘 다 21이 나와야 한다. Eclipse `Window → Preferences → Java → Installed JREs`에서 해당 JDK를 등록하고 프로젝트의 JRE도 21로 선택한다.

`app`이 목록에 없으면 `File → Import → General → Existing Projects into Workspace`에서 `AdvancedJavaProgramming\app`을 선택한다. `Copy projects into workspace`는 선택하지 않는다. 실제 코드 위치를 그대로 사용하기 위해서다.

프로젝트 우클릭 `Properties → Resource`의 인코딩은 UTF-8로 맞춘다.

### 01-2. Maven 폴더와 설정 만들기

Maven은 라이브러리를 내려받고, 정해진 폴더의 코드를 빌드하는 도구다. JavaFX는 JDK에 포함되지 않으므로 Maven으로 가져온다. Eclipse 설치에 포함된 Maven 실행 기능을 사용하면 당장 별도 `mvn` 설치는 필요 없다.

Eclipse에서 `app` 아래에 다음 파일·폴더를 직접 만든다.

```text
app/
  pom.xml
  src/
    main/
      java/
        board/
          client/
            BoardApplication.java
      resources/
    test/
      java/
```

`pom.xml`은 프로젝트에 필요한 라이브러리·빌드 규칙 목록이다. 아래는 첫 실행을 위한 설정 예제다. JavaFX 21.0.12와 실행 플러그인 0.0.8의 배포 여부를 공식 Maven 저장소에서 확인했다. 최종 버전 선택은 #33에서 기록한다.

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>
  <groupId>swu</groupId>
  <artifactId>sticky-board</artifactId>
  <version>0.1.0-SNAPSHOT</version>
  <properties>
    <maven.compiler.release>21</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
    <javafx.version>21.0.12</javafx.version>
  </properties>
  <dependencies>
    <dependency>
      <groupId>org.openjfx</groupId>
      <artifactId>javafx-controls</artifactId>
      <version>${javafx.version}</version>
    </dependency>
  </dependencies>
  <build>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-compiler-plugin</artifactId>
        <version>3.13.0</version>
      </plugin>
      <plugin>
        <groupId>org.openjfx</groupId>
        <artifactId>javafx-maven-plugin</artifactId>
        <version>0.0.8</version>
        <configuration>
          <mainClass>board.client.BoardApplication</mainClass>
        </configuration>
      </plugin>
    </plugins>
  </build>
</project>
```

`release=21`은 Java 21 규칙으로 컴파일한다는 뜻이다. `javafx-controls`는 버튼·라벨 등 화면 부품을 가져오며 필요한 JavaFX 기본 라이브러리도 함께 연결한다. `mainClass`는 실행 시작 클래스의 패키지 포함 이름이다.

프로젝트 우클릭 `Configure → Convert to Maven Project`를 실행한다. 이후 `Maven → Update Project…`를 눌러 반영한다. 이미 Maven 프로젝트라면 Convert 대신 Update만 한다. Source 목록에서 `src/main/java`가 소스 폴더로 잡혔는지 확인한다. 코드 파일은 기존 `src` 바로 아래에 만들지 않는다.

이 안내서는 `module-info.java` 없이 시작한다. FlatLaf는 Swing용 테마이므로 이 JavaFX 프로젝트에는 등록하지 않는다.

### 01-3. 버튼 하나로 실행 흐름 확인

`src/main/java`를 우클릭해 `New → Package → board.client`를 만들고, 그 안에 `BoardApplication` 클래스를 만든다. 파일명은 `BoardApplication.java`다.

먼저 “창을 띄우고 버튼을 클릭하면 글자가 바뀐다”는 의도를 아래처럼 읽는다.

```text
프로그램 시작
  JavaFX가 창 준비
  라벨과 버튼 생성
  버튼 클릭 시 라벨 문구 변경
  화면에 두 부품 배치
  창 표시
```

최소 실행 예제:

```java
package board.client;

import javafx.application.Application;
import javafx.scene.Scene;
import javafx.scene.control.Button;
import javafx.scene.control.Label;
import javafx.scene.layout.VBox;
import javafx.stage.Stage;

public class BoardApplication extends Application {
    @Override
    public void start(Stage stage) {
        Label status = new Label("아직 클릭하지 않았어요");
        Button button = new Button("확인");
        button.setOnAction(event -> status.setText("클릭 성공"));
        VBox root = new VBox(12, status, button);
        stage.setScene(new Scene(root, 800, 600));
        stage.setTitle("포스트잇 보드 — 실행 확인");
        stage.show();
    }

    public static void main(String[] args) {
        launch(args);
    }
}
```

`Application`은 JavaFX 앱의 기본 클래스다. `launch`가 JavaFX를 시작하면 `start(Stage)`가 호출된다. `Stage`는 창, `Scene`은 창 안의 화면, `VBox`는 부품을 세로로 놓는 배치 도구다. `setOnAction`은 Swing의 `addActionListener`처럼 클릭 후 실행할 동작을 연결한다.

### 01-4. Eclipse에서 실행

프로젝트 우클릭 `Run As → Maven build…`에서 다음을 확인한다.

1. Base directory: `app` 폴더.
2. Goals: `clean compile`.
3. JRE 탭: Temurin JDK 21.
4. Run을 눌러 `BUILD SUCCESS`를 확인한다.
5. Goals를 `javafx:run`으로 바꿔 실행한다. 첫 실행은 인터넷 연결이 필요하다.

앱이 열린 동안 실행 과정이 살아 있는 것은 정상이다. 창을 닫아 종료한다. 초반에는 Maven 실행을 기준으로 삼는다.

다른 PC에서도 같은 명령을 쓰려면 #33의 마지막 작업으로 Maven Wrapper를 만든다. Eclipse Maven Build의 Goals에 아래를 입력할 수 있다.

```text
org.apache.maven.plugins:maven-wrapper-plugin:3.3.4:wrapper -Dtype=only-script
```

생성된 `mvnw`, `mvnw.cmd`, `.mvn/wrapper/` 설정을 확인하고 버전·생성 파일을 기록한다. 이후 PowerShell에서는 `app` 안에서 다음을 사용한다.

```powershell
.\mvnw.cmd clean compile
.\mvnw.cmd javafx:run
```

Wrapper도 최초 실행에 인터넷과 JDK가 필요하다.

### 01-5. 완료 기준과 오류 해석

- [ ] 21로 컴파일되고 버튼 클릭 시 라벨이 바뀐다.
- [ ] 창 종료 후 실행이 종료된다.
- [ ] 빌드·실행 방법과 선택 버전을 기록했다.
- [ ] Wrapper로 같은 빌드를 재현했다.

| 보이는 오류 | 먼저 확인할 것 |
|---|---|
| `package javafx... does not exist` | pom.xml 위치·Maven Update·Maven Dependencies 확인 |
| `release version 21 not supported` | Maven 실행 설정의 JRE가 JDK 21인지 확인 |
| `Could not find ... main class` | 패키지·파일 위치와 mainClass가 일치하는지 확인 |
| `JavaFX runtime components are missing` | Maven의 javafx:run으로 실행했는지 확인 |
| 라이브러리 다운로드 실패 | 네트워크·프록시와 요청한 버전을 확인 |
| public class 파일명 오류 | BoardApplication과 파일명의 대소문자 일치 확인 |

오늘 회고: “main 다음에 누가 start를 호출하는가?”, “버튼 코드는 클릭할 때 실행되는가, 화면 생성 때 실행되는가?”를 자기 말로 설명한다.

## 02. 서버 없이 텍스트 카드 만들기 — #34

**복습:** 이벤트가 발생하면 데이터를 바꾸고 화면에 결과를 보여준다. 화면 부품 자체를 저장할 데이터로 쓰면 DB·통신 연결이 어려워지므로 카드 데이터와 화면을 나눈다.

**파일 책임:** `board.model.StickyNote`는 ID·작성자·글·좌표·표시 순서·버전 등의 데이터를 담는다. `board.client.ui.BoardView`는 보드와 버튼을, `StickyNoteView`는 한 카드와 편집창을 표시한다. 한 번에 모든 파일을 만들지 말고 카드 표시가 된 뒤 분리한다.

**작업:** 단계 01의 창에 보드 영역 `Pane`과 “글 추가” 버튼을 붙인다. 처음에는 고정된 글 카드 하나, 다음에는 입력창으로 글 받기, 마지막에는 수정·취소·삭제 순으로 넓힌다.

힌트: `TextInputDialog`로 글을 받고 `Label`로 표시할 수 있다. 다음은 보드 영역 안에 임시 카드 하나를 놓는 작은 실습이다.

```java
Pane board = new Pane();
Label note = new Label("첫 번째 메모");
note.relocate(40, 40);
board.getChildren().add(note);
```

`Pane`과 `Label`의 JavaFX import가 필요하다. 이 조각을 기존 Scene의 화면에 연결해 관찰한다. 이후 모델에서 화면을 만들도록 바꾼다.

```text
추가 버튼 클릭 → 입력창
취소면 종료
글 검사 → ID를 가진 카드 데이터 생성
목록에 저장 → 그 카드 화면 추가
수정·삭제도 ID로 대상 확인
```

**실패·완료:** 카드 두 개 중 하나만 수정·삭제되는지, 취소 시 글이 유지되는지, 500자/501자·300개/301개 경계가 맞는지 확인한다. 빈 글 정책은 직접 결정한다. 서버 연결 후에는 같은 검사를 서버에서도 한다.

**회고·리뷰:** 카드 ID 없이 화면 순서로 찾으면 삭제 후 어떤 문제가 생길까? 작성한 추가·수정·삭제 코드와 테스트 결과를 리뷰받는다.

## 03. 카드 옮기기와 겹침 순서 — #35

**복습:** 마우스를 누름·움직임·놓음은 서로 다른 이벤트다. 좌표 기준이 다르면 카드가 갑자기 다른 곳으로 튄다.

**작업:** 카드 하나에 이벤트를 연결한다. 누를 때 마우스와 카드 원점의 차이를 기억하고, 드래그 때 보드 좌표에서 그 차이를 뺀다. 화면 좌표는 `board.sceneToLocal(...)`로 보드 기준으로 바꿀 수 있다.

```text
누름 → 잡은 위치의 차이 기록
드래그 → 보드 좌표 변환 → 차이만큼 보정 → 화면 이동
놓음 → 최종 x·y를 모델에 반영 → 표시 순서 갱신
```

**파일 책임:** 처음에는 `StickyNoteView`에서 관찰하고, 이후 `BoardController`가 모델의 위치·순서를 변경하도록 분리한다. `toFront()`는 화면 순서만 바꾸므로 데이터의 표시 순서도 함께 갱신한다.

**실패·완료:** 카드 모서리를 잡아도 튀지 않고, 겹친 카드를 앞쪽으로 이동한 결과가 모델에 남아야 한다. 보드 밖 이동은 허용/제한 중 정책을 기록한다.

**회고·리뷰:** 같은 카드가 화면과 모델에서 다른 좌표를 가진 적이 있는지 확인한다.

<a id="step-04"></a>

## 04. 이미지 카드 — #36

**복습:** 파일 선택과 실제 이미지 읽기는 다른 단계다. 사용자 PC 경로만 저장하면 다른 PC에서는 그 이미지를 열 수 없다.

**작업:** `FileChooser`로 이미지 선택 → 취소 확인 → 파일 제한 검사 → 읽기 → `ImageView` 미리보기 순으로 만든다. 이미지 비율을 유지한다. 큰 이미지 처리는 `Task` 또는 작업 스레드에서 한다.

**파일 책임:** `ImageLoader`는 파일 검사·미리보기를 담당한다. 카드 모델에는 화면용 ImageView 대신 나중에 서버가 부여할 이미지 식별자를 담는다. 처음 로컬 실습에서는 임시 경로를 사용할 수 있으나 공유 구현 전에 바꾼다.

```text
선택 취소 → 아무 변경 없음
파일 검사 실패 → 이유 표시
읽기 성공 → 카드 생성·이미지 표시
서버 연결 이후 → 이미지 업로드 성공 → 카드 저장
```

**실패·완료:** 취소·깨진 파일·용량 초과에서 카드가 잘못 생성되지 않아야 한다. 느린 처리 중 창을 움직여 화면 응답을 확인한다. 이미지 형식·용량·픽셀 제한은 #36에서 선택·기록한다.

**회고·리뷰:** 파일 읽기 성공과 서버 저장 성공을 구분해 표시했는지 확인한다.

<a id="step-05"></a>

## 05. 작은 소켓 왕복과 화면 응답 — #37

**복습:** Socket은 클라이언트와 서버 사이 통신 연결이다. `readLine()`은 데이터가 올 때까지 기다릴 수 있으므로 버튼을 처리하는 화면 스레드에서 호출하면 화면이 멈춘다.

**작업:** `board.server.ServerMain`과 `board.client.net.SocketClient`를 만들고, 먼저 문자열 한 줄을 보내 그대로 받는 echo를 구현한다. 서버는 Eclipse의 Java Application, 클라이언트는 Maven javafx:run으로 별도 실행한다. 서버를 먼저 실행한다.

작은 실습의 송신 힌트:

```java
writer.write("PING\n");
writer.flush();
```

`writer`는 UTF-8로 연결된 출력 스트림이어야 한다. 줄바꿈은 한 메시지의 끝, flush는 버퍼 내용을 실제로 전달하는 동작이다. 이것만으로 완성된 통신 코드가 되지는 않는다.

```text
서버: 포트 대기 → 접속 받음 → 줄 읽음 → 응답
클라이언트: 연결 → PING 송신 → 수신 작업에서 응답 읽음
화면 반영: Platform.runLater로 상태 라벨 변경
```

실제 편집 메시지에는 종류·요청 ID·보드 ID·카드 ID·예상 버전·데이터·결과를 담는다. 줄 단위 JSON 등을 선택하고 길이·형식 검사를 정한다. 사용자 글의 줄바꿈은 직렬화하여 메시지 경계와 섞이지 않게 한다.

**실패·완료:** 두 클라이언트의 왕복을 확인하고 서버 미실행·연결 끊김을 안내한다. 창을 닫으면 소켓과 작업 스레드도 정리되어야 한다. 이 단계에서는 로컬 테스트용 통신만 확인한다.

**회고·리뷰:** “수신 스레드”와 “화면 변경 스레드”의 역할을 설명한다.

<a id="step-06"></a>

## 06. JDBC로 저장하고 다시 열기 — #38

**복습:** JDBC는 Java에서 DB에 명령을 보내는 기본 연결 방법이다. 화면을 닫아도 데이터를 남기려면 메모리 목록을 DB 저장으로 연결한다.

**선택:** 단일 Java 서버의 작은 실습에는 SQLite가 설치 부담이 작고, DB 동시 처리·서버 운영을 별도로 연습하려면 다른 관계형 DB를 검토할 수 있다. 제품·드라이버는 여기서 선택하고 Maven 버전을 고정한다. 모든 클라이언트가 자기 DB를 따로 수정하는 구조는 피하고 Java 서버가 저장을 담당한다.

**파일 책임:** `board.server.store.Database`는 연결 설정, `BoardRepository`·`NoteRepository`는 SQL 저장·조회, 모델은 데이터 값이다.

```text
DB 연결 확인 → 임시 카드 한 개 INSERT → SELECT로 비교
서버 재시작 → 다시 SELECT
성공하면 생성·조회·수정·삭제 요청을 Repository에 연결
```

힌트: 글을 SQL 문자열에 붙이지 않고 PreparedStatement의 `?`에 `setString` 등으로 값을 전달한다. try-with-resources로 Connection·Statement·ResultSet을 정리한다.

**실패·완료:** 한글·작은따옴표가 들어간 글이 보존되고 내용·작성자·좌표·순서·버전이 재시작 후 같아야 한다. DB 실패를 저장 성공으로 표시하지 않는다. 이미지 파일 저장 성공/DB 실패도 직접 재현한다.

**회고·리뷰:** 여러 저장이 모두 성공해야 할 때 트랜잭션이 필요한 이유를 설명한다.

<a id="step-07"></a>

## 07. 사용자와 세션 — #39

**복습:** 로그인은 비밀번호 확인이고 세션은 이후 요청이 어느 사용자의 것인지 서버가 기억하는 상태다.

**작업:** 검증된 비밀번호 해시 방식 선정 → 회원 저장 → 로그인 → 서버 세션 생성 → 로그아웃 순으로 구현한다. 비밀번호를 평문으로 저장하거나 일반 단순 해시만 적용하지 않는다. 이 기능은 검증된 방식의 API 활용을 학습한다.

**파일 책임:** `AuthService`는 인증 규칙, `UserRepository`는 사용자 저장, `SessionRegistry`는 로그인 연결과 사용자 관계다.

```text
로그인 요청 → 서버가 비밀번호 검증 → 연결에 사용자 연결
쓰기 요청 → 서버 세션으로 요청자 결정
로그아웃 → 세션 제거 → 이후 쓰기 거부
```

**실패·완료:** 중복 계정·잘못된 비밀번호·로그아웃 뒤 쓰기를 검사한다. 요청 데이터의 작성자 ID를 바꿔도 다른 사용자로 행동할 수 없어야 한다.

**회고·리뷰:** 화면에서 버튼을 숨기는 것과 서버에서 요청을 거부하는 것의 차이를 설명한다.

<a id="step-08"></a>

## 08. 보드 목록·공유 코드·권한 — #40

**복습:** 보드를 볼 수 있다는 것과 모든 카드를 바꿀 수 있다는 것은 별개의 권한이다.

**작업:** 내 보드 목록 → 생성 → 코드 참여 → 제목·코드 변경을 구현한다. 소유자는 전체 카드를, 참가자는 자기 카드를 관리한다. 참가 관계를 서버에 남긴다.

**파일 책임:** `BoardService`는 참여·소유자 규칙, `BoardRepository`는 저장, `BoardListView`는 목록 화면이다.

```text
요청 도착 → 로그인 확인 → 보드 접근 확인
보드 관리 요청 → 소유자 확인
카드 편집 요청 → 작성자 또는 소유자 확인
통과한 요청만 저장
```

**실패·완료:** 두 계정으로 타인의 카드·보드 관리 요청을 보내 거절을 확인한다. 변경한 이전 코드로 신규 참여가 안 되어야 한다. 코드 변경 후 기존 참가자를 유지할지는 결정하고 검증한다.

**회고·리뷰:** 권한 검사가 카드 생성·수정·이동·삭제에 모두 적용됐는지 확인한다.

<a id="step-09"></a>

## 09. 실시간 동기화와 수정 충돌 — #41

**복습:** 같은 카드의 오래된 내용을 보내면 다른 사람이 저장한 변경을 덮어쓸 수 있다. 버전은 요청이 어느 상태를 보고 작성됐는지 구분한다.

**작업:** 서버 승인 결과를 같은 보드의 모든 클라이언트에 보낸다. 카드마다 버전을 두고 요청의 예상 버전과 비교한다.

```text
요청 → 로그인·권한·글/카드 상한 검사
예상 버전 조건으로 DB 갱신 → 갱신 행 수 확인
실패 → 충돌 응답·최신 상태 안내
성공 → 버전 증가 결과를 같은 보드에 전달
```

**파일 책임:** `NoteService`는 검사와 변경, `BoardEventPublisher`는 대상 보드 연결에 전달, `BoardController`는 승인 결과를 화면에 반영한다.

**실패·완료:** 두 사용자의 동시 수정·이동·삭제를 시험한다. 이전 버전으로 수정하면 충돌을 알려야 한다. 카드 상한 검사와 삽입은 함께 보호하여 동시 생성으로 300개를 넘지 않게 한다. 다른 보드에는 이벤트가 가지 않아야 한다.

**회고·리뷰:** “확인 후 저장” 사이에 다른 요청이 들어올 수 있는 구간을 찾는다.

<a id="step-10"></a>

## 10. 재접속과 삭제된 보드 — #42

**복습:** 연결이 끊긴 동안 이벤트를 놓쳤으므로 다시 연결만 해서는 화면이 최신이 되지 않는다.

**작업:** 끊김 표시 → 재인증·권한 확인 → 보드 전체 최신 상태 수신 → 화면 교체를 구현한다. 처음에는 재연결 버튼으로 시작하고 자동 재시도는 필요할 때 도입한다.

```text
연결 끊김 → 편집/저장 상태 안내
재접속 → 인증·보드 접근 확인
최신 전체 상태 → 모델 교체 → 화면 재구성
삭제/접근 취소 → 해당 보드 편집 종료
```

**파일 책임:** `SocketClient`는 연결 상태, `BoardService`는 최신 조회·삭제 판정, Controller는 화면 복원이다.

**실패·완료:** 다른 클라이언트가 수정하는 동안 한 연결을 끊고 복원한다. 보드 전환 후 이전 보드 이벤트가 남지 않는지 확인한다. 재전송은 요청 ID 정책으로 중복 적용되지 않게 한다.

**회고·리뷰:** 아직 승인되지 않은 입력과 서버에 저장된 입력을 구분했는지 확인한다.

<a id="step-11"></a>

## 11. 스냅샷과 삭제 전 보관 — #43

**복습:** 스냅샷은 특정 시점의 보드를 이미지로 보존한 결과다. 그 이미지가 저장되지 않았는데 보드부터 삭제하면 결과를 잃는다.

**작업:** 카드 모델을 기준으로 최종 보드를 이미지로 만든다. 소유자 삭제 요청 때 최종 버전을 확인하고 저장 성공 후 삭제한다. 서버의 데이터가 기준이어야 하므로 사용자 PC가 보낸 이미지만으로 최종 상태를 판정하지 않는다.

```text
삭제 요청 → 소유자·최종 버전 확인
일관된 카드 목록 확보 → 이미지 생성·보관
저장 성공 → 보드 삭제·접속자 통보
저장 실패 → 보드 유지·실패 안내
```

**파일 책임:** `SnapshotRenderer`는 글·이미지·배치를 이미지로 변환, `SnapshotService`는 권한·저장·삭제 순서, `SnapshotRepository`는 메타데이터 저장이다. 클라이언트 화면 캡처로 최소 실습 후 서버 렌더링 방식과 삭제 중 편집 처리 정책을 결정한다.

**실패·완료:** 겹침과 이미지가 포함된 보드를 보존한다. 저장 실패 시 보드가 남고 재시작 후 이미지가 열려야 한다. 삭제 중 수정 요청을 넣어 스냅샷과 삭제 대상 상태가 일치하는지 확인한다.

**회고·리뷰:** DB 트랜잭션만으로 파일 저장까지 자동 취소되는지 검토한다.

<a id="step-12"></a>

## 12. 공개 갤러리와 스냅샷 삭제 — #44

**복습:** 공개 목록에서 숨기는 것만으로 이미지 접근이 막히지 않는다. 이미지 요청에도 권한 검사가 필요하다.

**작업:** 내 스냅샷 상세 → 공개/비공개 변경 → 공개 갤러리 → 소유자 삭제 순으로 만든다.

```text
목록·상세·이미지 요청 → 소유자 또는 공개 여부 확인
공개 변경·삭제 → 소유자 확인
변경 저장 → 버전 갱신 → 목록/상세 갱신
```

**파일 책임:** `SnapshotGalleryView`는 화면, `SnapshotService`는 공개·소유 규칙이다.

**실패·완료:** 비소유 계정으로 비공개 이미지 ID를 직접 요청하고 거절을 확인한다. 공개 해제·삭제 후 새 요청을 막는다. 이미 다운로드한 사본까지 회수하는 기능은 제공하지 않는다.

**회고·리뷰:** 목록·상세·이미지 경로가 같은 정책을 사용하는지 확인한다.

<a id="step-13"></a>

## 13. 썸네일 캐시 — #45

**복습:** 캐시는 받은 데이터를 잠시 재사용하는 기능이고 DB 저장과 다르다. LRU는 가장 오래 사용하지 않은 항목부터 버리는 규칙이다.

**작업:** 스냅샷 ID+버전으로 320×180 이하 썸네일을 최대 50개 보관한다. `LinkedHashMap`의 접근 순서 옵션을 작은 예제로 먼저 관찰한다.

```text
서버 권한·버전 확인
캐시 적중 → 기존 썸네일 표시
미적중 → 다운로드 → 캐시에 저장 → 표시
50개 초과 → 오래 사용하지 않은 항목 제거
공개 변경/삭제 → 해당 항목 제거
로그아웃 → 전체 제거
```

**파일 책임:** `ThumbnailCache`는 키·이미지·사용 순서, `ThumbnailService`는 권한 확인·다운로드·무효화다. 다운로드는 작업 스레드에서 수행하고 캐시 접근은 한 스레드로 모으거나 동기화 정책을 정한다.

**실패·완료:** 동일 버전 두 번 조회의 다운로드 횟수를 센다. 51개로 제거를 확인하고, 첫 항목을 다시 읽은 뒤 제거 순서가 달라지는지 확인한다. 권한 확인 실패와 로그아웃 뒤에는 캐시 이미지를 표시하지 않는다.

**회고·리뷰:** “캐시에 있음”과 “현재 열 권한이 있음”을 구분했는지 설명한다.

## 14. 통합·시연·회고 — #46

새 폴더에서 실행 안내만으로 서버와 클라이언트를 실행한다. 서버 주소·DB·이미지 저장 경로를 설정으로 분리하고 두 계정·두 클라이언트·두 보드로 테스트한다.

[PRD 검증표](기말프로젝트_PRD.md#6-검증-항목) V-01~V-14마다 실행 조건·기대 결과·실제 결과·증거·수정 내용을 남긴다. 통과하지 않은 항목은 그대로 기록한다.

5분 시연 순서: 접속 → 글·이미지 붙이기 → 카드 이동과 두 화면 동기화 → 저장·재조회 → 삭제 전 스냅샷 → 공개 갤러리. 준비된 계정과 이미지로 연습하고 실제 시간을 측정한다.

**완료:** 참고 서비스의 B-01~B-13을 모두 확인하고, 저장·실패·권한·충돌·캐시 검증과 직접 쓴 핵심 코드 설명을 마친다. 앱 기능·환경 설정·시연 데이터의 역할을 구분한다.
