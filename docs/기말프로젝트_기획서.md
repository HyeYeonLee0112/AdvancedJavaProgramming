# 기말 프로젝트 기획서 — 글·그림 릴레이 (가칭)

상태: 사용자 아이디어와 합의 내용을 정리한 작업 초안. 제출용 최종본 아님.

## 1. 기획 의도

참가자들이 하나의 소재로 이야기를 이어 쓰고, 다른 사람이 쓴 장면을 그림으로 해석한다. 마지막에 문장과 그림을 이야기 순서대로 공개하여 서로 다른 해석을 함께 즐긴다.

- 대상 사용 상황: 수업 발표에서 참가자들이 직접 체험하는 짧은 공동 창작 게임.
- 핵심 제약: 입장·설명·작성·결과 감상을 포함해 5분 이내 시연.
- 참여 인원: 4~6명. 게임 시작 시 참가자 명단을 고정한다.
- 작품: 독립 시나리오 여러 개가 아니라 N개의 장면으로 이루어진 하나의 이야기.
- 제품명: 미정.

## 2. 확정한 핵심 진행

1. 참가자가 방에 모이고 시작 소재를 받는다.
2. 참가자 순서를 정한다. 순서 결정 방식은 미정이다.
3. 첫 참가자가 20초 이내에 시작 문장을 쓴다.
4. 다음 참가자는 직전 문장 하나만 보고 다음 장면을 쓴다. 누적 이야기는 공개하지 않는다. 각 참가자가 한 문장씩 작성한다.
5. 모든 장면을 자기 문장의 작성자가 아닌 참가자에게 무작위로 하나씩 배정한다. 누락·중복 배정은 없어야 한다.
6. 모든 참가자가 동시에 60초 동안 배정받은 장면을 그린다.
7. 그림 시간이 끝나면 원래 문장 순서에 따라 완성된 스토리보드를 함께 본다.
8. 완성작 보관함에서 결과를 다시 열고 공개 여부를 관리한다.

## 3. 완성작 보관함 — 추가 확정

- 앱 종료·재실행 후에도 저장된 작품을 열 수 있다.
- 문장, 그림, 장면 순서, 글쓴이와 그린 사람의 연결을 보존한다.
- 시작 시 등록된 참가자 전원이 완성작을 공동 소유하며 각자의 보관함에서 조회한다. 중도 이탈해도 소유 관계는 유지한다.
- 작품은 기본 비공개이며 방 개설자만 공개/비공개를 변경한다. 참가자에게 시작 전에 이 규칙을 표시한다.
- 원본을 보존한 별도 편집본에서 자유 보드 기능을 사용할 수 있다.
- 공동 원본 전체 삭제 정책은 미정이다. 정책 확정 전에는 다른 참가자의 원본을 함께 삭제하는 기능을 제공하지 않는다.

### 기본 진행·실패 처리 정책

사용자가 위임한 시간 초과·이탈 처리는 다음 기본값으로 정한다.

- 서버가 시간과 차례를 판정한다. 초안은 변경 시 최대 초당 1회, 입력을 멈추면 빠르게 서버에 전달한다. 서버 수신 여부를 화면에 표시한다.
- 문장은 수동 제출 또는 20초 마감으로 확정한다. 마감 시 서버가 받은 마지막 비어 있지 않은 초안을 사용한다. 중복 제출은 한 번만 처리한다.
- 빈 문장으로 마감하면 고정 대체 문장 ‘그러던 중, 예상하지 못한 일이 벌어졌다.’를 넣는다. 첫 장면도 비면 ‘[소재]에 관한 이야기가 시작되었다.’를 사용한다. 결과에는 시스템 대체임을 표시한다.
- 그림은 펜, 펜 색상 선택, 지우개, 획 단위 되돌리기를 필수로 한다. 다시 실행·굵기 선택·전체 지우기는 선택 확장이다.
- 그림은 제출 전까지 수정 가능하다. 60초 마감 시 편집을 잠그고 자동 제출한다. 최종 전송 대기는 최대 5초이며, 실패하면 서버가 마지막으로 받은 그림 초안을 사용한다. 초안도 없으면 ‘그림 미제출’ 카드로 대체한다. 그림 초안은 변경된 경우 최대 5초마다 저장한다.
- 게임 중 신규 참가자는 받지 않는다. 연결이 끊겨도 타이머를 연장하거나 참가자 순서를 바꾸지 않는다. 같은 계정이 재접속하면 현재 단계와 허용된 초안을 복구한다.
- 이탈자의 차례도 마감 규칙으로 처리한다. 배정은 시작 명단 기준을 유지하며 다른 참가자에게 추가 그림을 요구하지 않는다.
- 방 개설자가 이탈해도 서버가 진행한다. 전원 이탈해도 서버가 살아 있으면 동일한 제한 시간으로 회차를 마무리한다. 서버 장애에서 자동 진행 복구는 초기 보장 범위 밖이며, 재접속 시 중단 상태를 표시한다.

## 4. 기존 협업 보드와의 관계

참고 서비스 `jungle-mini-project-board`의 구현 기능을 필수 기준선으로 유지한다. 상세 목록은 [PRD](기말프로젝트_PRD.md)에 기록한다.

게임 진행 중에는 차례와 비공개 규칙을 적용한다. 종료 후 편집본에서는 텍스트·이미지 카드 작성, 이동, 수정, 삭제 등의 자유 편집을 제공한다. 기록의 원본과 편집 결과를 구분한다.

## 5. 과목 응용

| 과목 내용 | 이 프로젝트에서 해결할 문제 |
|---|---|
| AWT·Swing 수업 | 별도 주차 실습으로 컴포넌트·레이아웃·이벤트의 기본 원리를 익히고 JavaFX 구현과 비교 |
| JavaFX | 방, 문장 입력, 그림판, 결과, 보관함 화면 구성 |
| 이벤트·그래픽 | JavaFX `Canvas`와 `GraphicsContext`를 이용한 펜 입력, 색 선택, 지우개·되돌리기, 그림과 장면 표시 |
| 멀티스레드 | 통신·이미지 처리 중 화면 응답 유지, 단계별 시간 처리 |
| 소켓 | 참가자 상태, 차례, 제출, 단계 전환과 공개 동기화 |
| MVC·CRUD | 화면·진행 규칙·저장 책임 분리와 보드·작품 관리 |
| JDBC | 문장·그림 참조·작성자·순서·공개 여부를 저장하고 다시 조회 |
| RMI | 최신 주차표의 필수 항목으로 확인되지 않음. 실제 수업 요구 확인 후 판단 |

### 개발 환경

- Eclipse, Temurin JDK 21, Maven, JavaFX를 사용한다.
- Maven으로 JavaFX와 이후 JDBC 드라이버 등 외부 라이브러리의 버전과 빌드를 관리한다.
- JavaFX 버전, DB 제품과 JDBC 드라이버는 기술 검증 후 고정한다.
- 수업의 중심 GUI 범위가 Swing이므로 프로젝트의 JavaFX 사용 허용 여부를 교수자에게 확인한다.

### 간단한 이미지 캐싱

완성작 보관함을 다시 열 때 같은 썸네일을 매번 서버에서 받지 않도록, 최근 조회한 썸네일을 클라이언트 메모리에 잠시 보관한다. 원본 그림은 캐시에 넣지 않으며 캐시는 앱을 종료하면 사라진다. 캐시가 있더라도 서버의 작품 조회 권한을 먼저 확인한다.

## 6. 비판적 검토와 미정 사항

- 시간 예산: 준비 30초, 글쓰기 80~120초, 그림 60초, 최종 전송 최대 5초, 감상 60초를 잡으면 235~275초다. 남은 25초 이상은 단계 전환·배정·네트워크 여유로 둔다. 실제 시연으로 300초 이내를 검증한다.
- 순차 글쓰기에서는 자기 작성 시간 외에 대기가 생긴다. 사용자 관찰로 지루함을 검증해야 한다.
- 4~6명에서 동일하게 글쓰기 20초/인, 그림 60초를 적용한다.
- 게임 중 소재와 자신의 현재 과제만 표시한다. 글쓰기 차례에는 직전 한 문장, 그림 단계에는 배정 문장 하나만 보여준다. 전체 이야기는 결과 공개 후 조회한다.
- 소재 공급 방식, 작품명, 공개 연출(전체/한 컷씩), 공동 원본 삭제 정책을 결정해야 한다.
- 개발은 1인 희망이나 수업의 1인 프로젝트 허용 여부를 확인해야 한다. 게임 참가자 수와 개발 팀원 수는 별개다.

## 7. 사용자가 보완할 내용

- 이 놀이를 선택한 본인의 이유와 예상 참가자.
- 종이 또는 최소 시제품으로 진행한 1회 테스트 결과: 실제 소요 시간, 기다림, 그림 작성 난이도, 공개 반응.
- 테스트를 근거로 현재 인원·시간·이탈 정책이 적절한지 평가한 결과.
- 본인이 그린 화면 스케치와 최종 시연 시나리오.
