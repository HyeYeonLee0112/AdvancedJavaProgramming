## 1. 시작 상태와 이번 결과물

#33의 창과 버튼이 실행되는 상태에서 시작한다. 서버와 DB는 아직 연결하지 않는다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

CRUD는 만들기·읽기·고치기·지우기의 네 동작이다. 먼저 한 PC 안에서 이 동작을 완성하면 통신 오류와 화면 오류를 섞지 않고 확인할 수 있다.

카드 데이터와 화면 부품을 나눈다. 데이터에는 ID와 글이 있고, Label은 그 글을 보여줄 뿐이다. 화면의 몇 번째 부품인지는 삭제 때 달라지므로 카드의 신분증으로 사용할 수 없다.

## 3. 지금 정할 것과 미룰 것

- 지금: 메모리 목록과 카드 ID로 관리한다. 저장 구조를 이해하기 쉽다.
- 짧게 이해: 작성자·좌표·순서·버전은 뒤 단계가 사용할 데이터다. 현재는 임시 작성자와 기본값으로 시작한다.
- 나중: 서버 권한·영구 저장은 #38~#41에서 연결한다.
- 제외: 색상·서식·자동 저장을 동시에 확장하지 않는다.

빈 글 허용 여부와 500자를 세는 방식은 구현 전 기록한다. Java String.length는 이모지 하나를 2로 셀 수 있다. 화면과 서버가 같은 기준을 쓰도록 테스트 사례를 남긴다.

## 4. 파일별 책임과 연결

| 제안 파일 | 입력 → 출력 | 맡길 일 / 맡기지 않을 일 |
|---|---|---|
| board/model/StickyNote.java | ID·글 등 → 카드 값 | 화면 부품을 담지 않는다. |
| board/client/ui/BoardView.java | 카드 목록 → 보드 화면 | 추가 버튼과 카드 영역. SQL은 넣지 않는다. |
| board/client/ui/StickyNoteView.java | 카드 값 → 한 카드 화면 | 글 표시·편집 요청. 다른 카드 관리 제외. |
| board/client/BoardController.java | 사용자 입력 → 모델 변경·화면 갱신 | ID로 대상을 찾고 검사한다. |

처음에는 실행 클래스 안에서 작은 예제를 확인하고, 동작한 뒤 위 책임으로 나눈다. 이름은 제안이며 실제 작성한 이름을 기록한다.

## 5. 사람의 의도 → 실행 흐름

사용자가 글을 입력하면 카드 하나가 생긴다. 수정은 기존 카드를 바꾸는 것이지 새 카드를 만드는 것이 아니다.

```text
추가 버튼 → 입력창 → 취소면 종료
입력 검사 → 한도 검사 → 새 ID와 데이터 생성 → 목록에 추가 → 표시
수정 요청 → ID로 대상 찾기 → 입력창에 기존 글 표시
취소면 유지 / 저장이면 검사 후 기존 데이터와 화면 변경
삭제 요청 → ID로 대상 찾기 → 목록과 화면에서 같은 카드 제거
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

#33의 start 안에서 라벨과 버튼 실습 대신 임시로 넣는다. 추가 import는 javafx.scene.layout.Pane, javafx.scene.control.Label이다. root 대신 board를 Scene에 넣는다.

```java
Pane board = new Pane();
Label note = new Label("첫 번째 메모");
note.setPrefSize(180, 100);
note.setWrapText(true);
note.relocate(40, 40);
board.getChildren().add(note);
```

Pane은 부품을 담는 보드 영역, Label은 글 표시 부품이다. relocate(40, 40)은 보드 기준 위치이고 getChildren().add는 화면에 붙인다. 이 예제에는 입력·모델·수정·삭제가 없다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 예제의 카드 하나가 보이는지 확인한다. 글과 위치를 바꿔 본다.
2. TextInputDialog로 추가 입력을 받는다. 취소 반환과 빈 문자열을 구분한다.
3. StickyNote에 ID·글을 담고 목록의 데이터로 화면을 만든다.
4. 카드 두 개를 만들고 각각 ID로 찾아 편집한다. 저장과 취소를 따로 확인한다.
5. 삭제 시 데이터 목록과 화면에서 같은 ID가 사라지는지 확인한다.
6. 500자·300개 검사와 안내 문구를 추가한다. 300개 테스트는 임시 생성 반복으로 준비해도 되지만 실제 처리 경로를 사용한다.
7. 직접 쓴 코드를 파일 책임에 맞게 나눈다. 테스트용 대량 생성 버튼은 제품 화면에서 분리한다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| A·B 카드 생성 후 A만 수정 | B는 유지, A의 ID 유지 | 리스트 위치로 대상을 찾는지 |
| 수정창에서 취소 | 이전 글 유지 | 입력 중 원본 모델을 바꾸는지 |
| A 삭제 후 B 수정 | B만 변경 | 삭제 후 인덱스 변화 |
| 500자 / 501자 입력 | 전자는 허용, 후자는 이유 안내 | UI와 검사 기준 |
| 299개에서 1개 추가 후 다시 추가 | 300개까지, 301번째 거부 | 검사 시점 |
| 한글·줄바꿈·이모지 | 표시와 길이 기준 일관 | 글자 계산 정책 |
| 빈 글·공백만 입력 | 기록한 정책과 일치 | trim 적용과 취소 혼동 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 두 카드의 수정·삭제가 독립적으로 동작한다.
- [ ] 취소 시 카드 개수·내용이 바뀌지 않는다.
- [ ] 500/501자와 300/301개 경계를 재현해 기록한다.
- [ ] 모델에서 JavaFX 부품을 제거하고 카드 ID로 연결한다.

리뷰 질문: 왜 삭제 후 인덱스로 카드를 찾으면 위험한가? 입력 검사는 화면과 데이터 변경 중 어디에 있는가? 추가·수정·삭제 코드와 경계 테스트 결과를 가져온다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
