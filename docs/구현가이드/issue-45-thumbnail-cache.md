# #45 · 썸네일 LRU 캐시

320×180 이하 썸네일을 최대 50개 재사용한다. 가장 오래 안 본 항목을 제거하고, 로그아웃·삭제·공개 변경 뒤 오래된 이미지를 보여주지 않는다.

## 1. 시작 상태와 이번 결과물

#44의 권한·공개 변경·버전·이미지 조회가 먼저 동작해야 한다. 캐시 없이도 보관함이 열리는 상태에서 추가한다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

캐시는 받은 데이터를 잠시 재사용해 중복 다운로드를 줄이는 임시 보관이다. 영구 저장 DB와 달리 비워도 기능이 동작해야 한다. LRU는 가장 오래 사용하지 않은 항목을 먼저 버리는 규칙이다.

캐시 적중은 지금 볼 권한이 있다는 뜻이 아니다. 최신 서버 권한/버전을 확인한 뒤 같은 ID+버전의 썸네일을 재사용한다. 권한 확인 요청까지 없애는 최적화는 하지 않는다.

## 3. 지금 정할 것과 미룰 것

- 지금: 클라이언트 메모리, 썸네일만, ID+버전 키, 최대 50개.
- 짧게 이해: LinkedHashMap 접근 순서는 get한 항목을 최근 사용으로 옮긴다.
- 결정 필요: 캐시 접근을 한 작업에 모을지 잠금으로 보호할지. 순서 변경을 포함하므로 단순 읽기도 동시성 검토가 필요하다.
- 나중: 디스크 캐시·원본 캐시·서버 캐시.

공개 변경 소식을 못 받았더라도 다음 조회에서 권한을 확인한다. 기존 화면의 이미지는 로그아웃·권한 회수 시 제거한다. 이 정책은 이미 사용자가 저장한 사본의 회수를 의미하지 않는다.

## 4. 파일별 책임과 연결

| 제안 파일 | 입력 → 출력 / 책임 |
|---|---|
| client/cache/ThumbnailKey.java | 스냅샷 ID+버전 → 동일성 비교 |
| client/cache/ThumbnailCache.java | 키·이미지 → 재사용/저장/50개 제한·카운터 |
| client/image/ThumbnailService.java | 서버 권한·버전 확인 → 캐시/다운로드 결과 |
| client/ui/SnapshotGalleryView.java | 결과 표시·로딩/실패 대체 화면 |
| client/BoardController.java 또는 인증 담당 | 로그아웃·변경 알림→무효화 |

ThumbnailCache가 인증 서버가 되어서는 안 된다. ThumbnailService가 최신 권한 확인 후 캐시를 사용한다.

## 5. 사람의 의도 → 실행 흐름

같은 썸네일을 다시 볼 때 이미지 다운로드는 줄이되, 비공개로 바뀐 이미지를 캐시가 계속 열어주면 안 된다.

```text
조회 → 서버에 현재 접근권한·버전 확인
거절 → 해당 캐시/표시 제거 → 종료
허용 → ID+버전 조회 → 적중이면 기존 썸네일
미적중 → 작업 스레드 다운로드/축소 → 저장 → 표시
50개 초과 → 가장 오래 미사용 항목 제거
삭제/공개 변경 → 해당 ID의 모든 버전 제거
로그아웃 → 전부 비우고 화면/진행 작업 무효화
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

LRU 순서만 이해하는 독립 main 실습이다. import java.util.LinkedHashMap이 필요하다. 실제 이미지/권한/50개 제한은 포함하지 않는다.

```java
var cache = new LinkedHashMap<String, String>(16, 0.75f, true);
cache.put("A", "썸네일 A");
cache.put("B", "썸네일 B");
cache.get("A");
System.out.println(cache.keySet());
```

출력은 [B, A]다. true는 삽입 순서 대신 접근 순서를 사용한다. A를 읽어서 최근 항목이 되었다. 이 컬렉션이 알아서 50개로 제한해주는 것은 아니다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 예제에서 true를 false로 바꿔 순서 차이를 관찰한다.
2. 이미지 대신 문자열을 저장하는 작은 캐시로 get·put·제거·clear를 직접 구현한다. 한도를 3으로 낮춰 시험한다.
3. 키를 ID+버전으로 바꾸고 최신 버전이 다르면 이전 결과를 사용하지 않게 한다.
4. 320×180 이내·비율 유지 썸네일을 만들고 원본 이미지 참조가 캐시에 들어가지 않게 한다.
5. 권한 확인 성공 뒤 캐시 조회/다운로드를 연결한다. 다운로드 실패는 대체 화면으로 처리한다.
6. 50개 제한과 적중·미적중·제거 카운터를 연결한다. 화면 스레드에서 다운로드하지 않는다.
7. 공개 변경·삭제에서 ID에 해당하는 모든 버전을 비우고 로그아웃은 전체를 비운다.
8. 다운로드 도중 로그아웃/권한 변경이면 늦게 도착한 이미지가 다시 화면이나 캐시에 들어가지 못하게 한다.
9. 같은 키의 동시 다운로드를 합칠지 정책을 정한다. 최소한 중복 다운로드 여부는 측정해 한계를 기록한다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| 같은 ID·버전 두 번 조회 | 이미지 다운로드 1회, 권한 확인은 수행 | 키·호출 위치 |
| 1~50 저장 후 51 저장 | 1 제거, 최대 50 | 한도 검사 |
| 1~50 저장 후 1 조회→51 저장 | 2 제거, 1 유지 | 접근 순서 |
| 같은 ID의 버전 변경 | 이전 버전 재사용 안 함 | 키·무효화 |
| 비공개 전환 뒤 재조회 | 권한 거절, 캐시 표시 없음 | 권한 선행 |
| 로그아웃 중 다운로드 완료 | 재삽입/표시 없음 | 작업 세대/취소 |
| 캐시 비움/다운로드 실패 | 보관함은 대체 표시로 동작 | 캐시 의존성 |
| 가로·세로 썸네일 | 두 축 한도 이내 | 비율 유지 축소 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 320×180 이하·최대 50개·ID+버전 규칙을 지킨다.
- [ ] LRU 제거 순서와 중복 다운로드 감소를 카운터로 보인다.
- [ ] 권한 확인 뒤 표시하고 삭제·공개 변경·로그아웃에 무효화한다.
- [ ] 늦은 다운로드·캐시 실패가 잘못된 표시로 이어지지 않는다.

리뷰 질문: 권한 확인을 매번 하면 캐시는 무엇을 절약하는가? 왜 get도 동시성 검토 대상인가? 캐시 API·무효화·카운터와 51개 테스트를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
