## 1. 시작 상태와 이번 결과물

#33의 JavaFX 화면이 필요하다. 아직 실제 카드 동기화가 아니라 두 프로세스의 작은 왕복부터 만든다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

Socket은 프로그램 사이의 통신 연결이다. TCP는 바이트 흐름이므로 한 번 write한 내용이 한 번 read로 들어온다는 보장은 없다. 메시지 끝을 정해야 구분할 수 있다.

readLine은 줄 끝이나 연결 종료까지 기다릴 수 있다. 이 대기를 화면 스레드에 넣으면 클릭 처리가 멈춘다. 수신은 별도 작업에서, 화면 변경은 JavaFX 스레드에서 한다.

## 4. 파일별 책임과 연결

| 제안 파일 | 입력 → 출력 / 책임 |
|---|---|
| server/ServerMain.java | 포트 설정 → 접속 대기, 종료 관리 |
| server/ClientHandler.java | 한 연결의 입력 → 응답, 자원 정리 |
| client/net/SocketClient.java | 요청 → 송신, 수신 작업·연결 상태 |
| protocol/Message.java | 값 → 통신 형식의 데이터; 화면 객체 제외 |
| client/BoardController.java | 수신 결과 → 화면 갱신 예약 |

한 소켓 출력에 여러 작업이 동시에 쓰면 메시지가 섞일 수 있다. 송신을 한 큐/작업으로 모으는 등 순서를 보장할 정책을 정한다.

## 5. 사람의 의도 → 실행 흐름

버튼을 누르면 PING을 보내고 서버의 응답을 화면에서 본다. 서버가 없어도 멈춤 대신 연결 실패를 안내한다.

```text
서버 시작 → 포트 열기 → accept → 연결별 수신 작업
클라이언트 연결 → UTF-8 writer/reader 준비
버튼 → 송신 작업에 PING 전달 → 줄 끝과 flush
수신 작업 → readLine → 응답 해석 → 화면 변경 예약
창 종료 → 소켓 닫기 → 작업 종료 → 남은 자원 정리
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

SocketClient를 직접 작성한 뒤 송신 메서드에서 적용할 작은 조각이다. writer는 Socket 출력으로 만든 UTF-8 BufferedWriter이며 메서드에서 IOException을 처리해야 한다.

```java
writer.write("PING\n");
writer.flush();
```

write는 버퍼에 쓰고 flush는 보낼 내용을 밀어낸다. 줄바꿈은 readLine의 경계다. 수신 화면 연결은 import javafx.application.Platform 후 다음 원리를 사용한다.

```java
Platform.runLater(() -> status.setText("응답 도착"));
```

status는 기존 Label이다. 작업 스레드가 직접 setText하지 않도록 예약한다. 이것만으로 연결·수신·종료 전체가 구현되지는 않는다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. ServerSocket으로 한 클라이언트의 한 줄을 받아 돌려주는 console 실습을 직접 쓴다.
2. 콘솔 클라이언트로 PING 왕복을 확인한다. 줄바꿈이나 flush를 빼고 차이를 관찰한다.
3. 연결별 작업으로 두 클라이언트를 받는다. 수신 종료(null)와 IOException을 구분해 정리한다.
4. 서버를 Eclipse Java Application으로 먼저 실행하고, JavaFX 클라이언트를 Maven javafx:run으로 실행한다.
5. JavaFX의 버튼은 송신을 요청만 하고 대기하지 않는다. 수신 결과를 runLater로 표시한다.
6. JSON을 선택하면 의존 버전을 확인하고 메시지 형식 예시를 직접 정한다. 글의 줄바꿈이 실제 메시지 경계와 섞이지 않게 직렬화한다.
7. 최대 크기 검사는 readLine 이후만 하면 이미 큰 입력을 할당했을 수 있다. 실제 프로토콜에 제한된 읽기 방식을 정한다.
8. 창 종료·서버 종료에 소켓과 실행 작업을 정리하고 포트를 재사용할 수 있는지 확인한다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| 두 클라이언트 PING | 각각 응답 | 한 연결만 처리하는 루프 |
| 서버 안 켜고 접속 | 오류 안내, 창 반응 | 연결 대기 위치·시간 |
| 서버 종료 중 수신 | 끊김 표시, 반복 오류 폭주 없음 | null·예외 뒤 루프 탈출 |
| 한글·줄바꿈 있는 실제 메시지 | 내용 보존·경계 유지 | UTF-8·직렬화 |
| 잘못된/과대 메시지 | 제한 오류 또는 연결 종료 정책 | 읽기 제한·파싱 |
| 창 닫고 다시 실행 | 이전 연결·작업 종료 | close와 executor 종료 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 두 연결의 요청·응답을 확인한다.
- [ ] 요청 ID·메시지 경계·오류 형식·상한을 기록한다.
- [ ] 느린/실패한 통신에서 화면이 반응한다.
- [ ] 종료 시 소켓과 작업이 남지 않는다.

리뷰 질문: 한 번 write하면 상대 read도 한 번인가? 왜 flush가 필요한가? 서버 수신 루프·클라이언트 수신 작업·화면 갱신·종료 코드를 리뷰받는다.
