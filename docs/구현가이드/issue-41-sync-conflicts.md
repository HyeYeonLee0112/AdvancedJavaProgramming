# #41 · 보드별 동기화·동시 수정 충돌

두 클라이언트의 상태가 서버 승인 결과로 일치한다. 같은 이전 버전의 요청은 조용히 덮어쓰지 않고, 다른 보드로 이벤트가 새지 않는다.

## 1. 시작 상태와 이번 결과물

#35·#36의 카드 동작, #37의 통신, #40의 보드/권한 검사가 필요하다. 서버가 저장 결과를 판정할 수 있어야 한다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

A와 B가 버전 3을 보고 수정하면 A의 저장 뒤 B가 이전 내용으로 덮을 수 있다. 예상 버전은 요청자가 본 버전이고, 조건부 갱신은 그 버전일 때만 변경하는 방법이다.

원자적 처리는 중간에 다른 요청이 끼어들지 못하도록 검사와 변경을 하나의 보호된 작업으로 묶는 것이다. 버전 확인 후 별도 저장만 하면 경쟁이 남는다.

## 3. 지금 정할 것과 미룰 것

- 지금: 편집 결과는 서버가 승인한다. 충돌이면 최신 값을 받아 사용자가 다시 판단한다.
- 짧게 이해: 같은 보드 구독 연결만 이벤트 대상이다. 작성자에게도 결과를 한 번만 적용하도록 요청 ID를 사용한다.
- 결정 필요: 보드별 작업 큐/잠금과 DB 조건부 갱신의 조합. 단일 서버 기준으로 먼저 정한다.
- 나중: 복잡한 자동 병합·분산 서버·이벤트 영구 재생.

글 500자·카드 300개 검사는 UI 편의 검사와 서버 최종 검사 둘 다 필요하다. 299개에서 두 생성이 동시에 들어오는 경우를 반드시 재현한다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/service/NoteService.java | 인증·권한·입력·버전·한도 검사와 변경 경계 |
| server/store/NoteRepository.java | 예상 버전 조건으로 갱신·영향 행 수 반환 |
| server/event/BoardEventPublisher.java | 해당 보드의 승인된 결과 전달 |
| server/session/BoardSubscriptions.java | 연결↔현재 보드 관계 |

DB 변경과 네트워크 송신을 같은 성공이라고 보지 않는다. 저장 후 송신 실패는 #42의 최신 조회로 복구한다.

## 5. 사람의 의도 → 실행 흐름

사용자는 자기 변경의 저장 여부를 알고, 다른 사람의 최신 변경이 덮이지 않았다는 것을 믿을 수 있어야 한다.

```text
요청 → 세션·보드·카드 관계·권한·입력 확인
보호된 변경 구간에서 예상 버전 조건으로 저장
0행: 없음/충돌 구분 → 최신값과 오류 안내
성공: 새 버전·위치·순서 포함 결과 → commit
commit 이후: 같은 보드 구독자에게 이벤트
클라이언트: 요청/이벤트 중복 확인 → 서버 상태 반영
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

버전 비교의 가장 작은 main 실습이다. DB의 최종 동시성 처리는 별도로 구현해야 한다.

```java
int storedVersion = 4;
int expectedVersion = 3;
boolean canUpdate = storedVersion == expectedVersion;
System.out.println(canUpdate ? "변경 가능" : "충돌");
```

결과는 충돌이다. DB에서는 UPDATE의 WHERE에 id·board_id·version 조건을 함께 두고 변경 행 수를 확인하는 방향으로 확장한다. 이 if를 서버에서 읽고 나중에 저장하는 것만으로는 원자성이 보장되지 않는다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 카드 생성·수정·이동·삭제의 요청/결과 예시를 직접 작성한다. 오류 종류와 서버 버전을 넣는다.
2. 한 클라이언트에서 서버 commit 이후 승인된 모델로 화면을 갱신한다. 전송 성공은 저장 성공이 아니다.
3. 같은 보드의 두 클라이언트로 전파한다. 다른 보드 연결은 제외한다.
4. 응답과 이벤트를 모두 받는 작성자에게 동일 변경이 두 번 적용되지 않게 한다.
5. 수정·이동·삭제 모두 예상 버전을 검사한다. 카드 자체가 없어진 경우도 충돌/없음 정책으로 안내한다.
6. 충돌 시 최신 값을 보여주고 자동 덮어쓰기 대신 재입력을 선택하도록 한다.
7. 카드 상한 검사와 삽입을 같은 보호 구간에 둔다. 보드별 잠금을 쓴다면 모든 생성·삭제 경로가 같은 규칙을 따른다.
8. 보드 표시 순서 할당도 동시에 같은 값으로 경쟁하지 않도록 변경 경계에 포함한다.
9. UI 임시 드래그와 서버 확정 위치를 구분하고 거절 시 최신 위치로 되돌린다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| A·B 같은 보드에서 CRUD·이동 | 내용·위치·순서·버전 일치 | 승인 이벤트 필드 |
| A·B 같은 버전으로 수정 | 하나 승인, 다른 하나 충돌 | 조건부 갱신 |
| 수정 vs 이동/삭제 동시 요청 | 정책에 맞는 충돌, 유실 없음 | 모든 경로의 버전 |
| 299개 상태에서 두 동시 생성 | 300개 이하 | 검사+삽입 보호 |
| UI를 우회해 501자 전송 | 서버 거절 | 서버 검증 |
| C는 다른 보드 구독 | A 보드 이벤트 없음 | 대상 목록 |
| 승인 응답+이벤트 중복 도착 | 카드 하나·일치 상태 | 요청 ID/버전 처리 |
| DB 실패 | 승인·전파 없음 | commit 전 전파 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 두 클라이언트에서 결과가 일치한다.
- [ ] 수정·이동·삭제 충돌과 299개 동시 생성을 검증한다.
- [ ] 서버에서도 500자·300개·권한을 검사한다.
- [ ] 다른 보드 전파·중복 반영이 없고 실패를 성공으로 보이지 않는다.

리뷰 질문: 버전 읽기와 저장 사이에 어떤 요청이 끼어들 수 있는가? 카드 상한과 순서 갱신은 어디에서 보호하는가? 변경 경계·조건부 SQL·전파·충돌 화면 코드를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
