# #38 · JDBC 저장·카드 복원

Java 서버가 데이터를 저장하고, 서버를 완전히 재시작해도 내용·작성자·좌표·순서·버전이 복원된다. 저장 실패는 성공으로 보이지 않는다.

상태: 학습·구현 안내서. 아래 동작은 완료 목표이며 현재 구현됐다는 뜻이 아니다.

## 1. 시작 상태와 이번 결과물

#34·#35의 카드 값과 #37의 요청·응답이 필요하다. 인증 전에는 로컬 학습용 임시 계정을 사용하고 외부에 서비스하지 않는다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

메모리 목록은 프로세스 종료와 함께 사라진다. JDBC는 Java에서 관계형 DB에 질의하는 기본 API다. DB 제품이 정해지면 그 제품의 드라이버를 Maven으로 연결한다.

Repository는 SQL을 모은 저장 담당 클래스다. 화면 이벤트마다 SQL을 섞지 않으면 저장 실패를 한 곳에서 다루고 파일 없이 화면을 시험하기도 쉽다.

## 3. 지금 정할 것과 미룰 것

- 지금: 단일 서버가 DB를 다룬다. 클라이언트마다 DB 파일을 따로 변경하지 않는다.
- 결정 필요: SQLite처럼 설치가 단순한 DB 또는 별도 DB 서버. 설치 부담·동시 쓰기·수업 환경을 비교하고 제품과 드라이버 버전을 기록한다.
- 짧게 이해: 트랜잭션은 여러 DB 변경을 모두 성공하거나 모두 취소하도록 묶는다.
- 나중: 권한·조건부 버전 갱신은 #39~#41.
- 제외: ORM 프레임워크로 JDBC 실습을 대체하기.

DB 제품별 잠금·타입·SQL 차이를 확인한다. JDBC Connection 한 개를 모든 클라이언트 작업에 무심코 공유하지 않는다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/store/Database.java | 설정을 읽어 DB 연결 제공 |
| server/store/NoteRepository.java | 카드 값의 저장·조회·수정·삭제 SQL |
| server/store/BoardRepository.java | 보드와 참가 관계 저장 |
| server/service/NoteService.java | 업무 검사 후 저장, 성공/실패 결과 생성 |
| src/main/resources/의 스키마 파일 | 처음 DB 준비 방법; 최종 테이블은 직접 설계 |

사용자→소유 보드, 보드→카드·참가자, 스냅샷→소유자·이미지의 관계를 종이에 그린 뒤 키를 정한다. 이후 삭제될 보드 때문에 보존할 스냅샷까지 연쇄 삭제되지 않도록 설계한다.

## 5. 사람의 의도 → 실행 흐름

서버가 저장을 끝냈다고 답해야 클라이언트가 저장 성공을 보여준다. 다시 접속할 때 DB의 값을 기준으로 화면을 만든다.

```text
드라이버·DB 경로 선택 → 테스트용 스키마 준비
한 카드 INSERT → SELECT → 값 비교 → 서버 종료
서버 다시 시작 → 같은 DB에서 SELECT → 복원 확인
실제 요청 → 검사 → Repository 저장 → commit 성공 → 응답
실패 → rollback/자원 정리 → 실패 응답 → 화면에 재시도 안내
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

드라이버와 DB 연결을 준비한 뒤 별도 저장 실습 메서드에서 적용한다. import java.sql.Connection, java.sql.PreparedStatement가 필요하다. database.open은 직접 작성할 연결 메서드이고 notes/text/id는 본인이 정한 스키마와 맞춰야 한다.

```java
try (Connection connection = database.open();
     PreparedStatement statement = connection.prepareStatement(
         "UPDATE notes SET text = ? WHERE id = ?")) {
    statement.setString(1, "오늘의 메모: '자바'");
    statement.setString(2, noteId);
    int rows = statement.executeUpdate();
    System.out.println("변경 행: " + rows);
}
```

?는 SQL에 붙이지 않고 값으로 전달하는 자리다. executeUpdate는 바뀐 행 수를 반환한다. try-with-resources는 자원을 닫는다. 이 작은 실습은 권한·버전·다중 SQL 트랜잭션이 없으므로 최종 편집 처리로 그대로 사용하지 않는다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. DB 후보와 선택 이유를 이슈에 남기고 공식 드라이버 버전을 확인해 pom에 추가한다.
2. DB 경로/접속 정보를 설정으로 분리한다. 저장소에 실제 비밀번호를 올리지 않는다.
3. 최소 카드 필드로 INSERT·SELECT를 먼저 성공시킨다. 전체 스키마는 직접 확장한다.
4. 한글·따옴표·줄바꿈·좌표·순서·버전 값을 넣고 조회 값과 하나씩 비교한다.
5. 프로세스를 종료하고 같은 DB로 재시작한다. 다른 작업 폴더에서도 DB 위치가 의도대로인지 확인한다.
6. 서버 요청을 Repository에 연결하고, 완료된 commit 뒤에만 성공 응답을 만든다.
7. 여러 DB 변경은 하나의 연결·트랜잭션 경계를 사용한다. 예외 시 rollback하고 연결을 정리한다.
8. 이미지 업로드 임시 파일→DB 기록→성공/실패 정리 순서를 기록한다. DB rollback이 파일도 지워주지는 않는다.
9. 스키마 초기화/업데이트와 테스트 DB 초기화 절차를 구분한다. 기존 사용자 DB를 테스트 때 지우지 않는다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| 한글·따옴표 저장 | 원문 보존 | 문자열로 SQL 연결 여부 |
| 종료·재시작 후 조회 | 모든 카드 값 동일 | 저장 경로·누락 필드 |
| 없는 ID 수정 | 0행 결과로 실패/없음 안내 | 행 수 무시 |
| DB 연결·쓰기 실패 | 성공 응답 없음 | commit 전 성공 표시 |
| 두 SQL 중 두 번째 실패 | 함께 취소 | 같은 연결·트랜잭션 여부 |
| 이미지 파일 성공·DB 실패 | 보드 변경 없음, 파일 정리 정책 작동 | 파일 보상 처리 |
| 저장이 느린 상태에서 클릭 | UI 반응 | 서버/클라이언트 작업 분리 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] DB와 드라이버·초기화 방법이 기록된다.
- [ ] 재시작 후 내용·작성자·x·y·순서·버전이 일치한다.
- [ ] PreparedStatement와 자원 정리를 적용한다.
- [ ] 저장·파일 일부 실패 테스트를 남기고 성공을 잘못 표시하지 않는다.

리뷰 질문: DB 위치가 상대 경로면 실행 폴더가 달라질 때 무엇이 생길까? commit 성공과 이미지 파일 성공은 같은가? 선택 근거·직접 만든 관계도·저장/조회·실패 처리 코드를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
