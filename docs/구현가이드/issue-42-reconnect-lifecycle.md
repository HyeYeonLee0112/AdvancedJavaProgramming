# #42 · 재접속·보드 삭제·접속 권한 변경

끊긴 동안 놓친 변경을 전체 최신 조회로 복구한다. 삭제·접근 회수 후 편집을 막고 이전 보드 구독을 정리한다.

상태: 학습·구현 안내서. 아래 동작은 완료 목표이며 현재 구현됐다는 뜻이 아니다.

## 1. 시작 상태와 이번 결과물

#41의 동기화된 보드가 필요하다. 최종 삭제의 스냅샷 선행 조건은 #43에서 붙이므로 여기서는 삭제된 보드의 요청/이벤트 처리부터 시험한다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

연결 복구는 데이터 복구가 아니다. 접속하지 못한 동안 서버 상태가 바뀌었을 수 있으므로 재인증과 최신 보드 조회가 필요하다.

연결 상태를 단순 true/false로만 두면 로그인 전인데 편집을 허용하기 쉽다. 끊김·연결 중·인증 중·보드 읽는 중·준비 완료를 구분한다.

## 3. 지금 정할 것과 미룰 것

- 지금: 사용자가 누르는 재연결 버튼과 전체 상태 교체. 이해·재현이 쉬운 방식이다.
- 결정 필요: 승인 응답을 잃은 요청의 처리. 자동 재전송하지 않고 최신 조회로 확인하는 단순 정책부터 검토한다.
- 나중: 자동 재시도/간격 조절·영구 중복 요청 기록.
- 제외: 끊긴 상태의 오프라인 편집 자동 병합.

전체 상태 수신과 구독 시작 사이에 변경을 놓칠 수 있다. 서버의 같은 보드 작업 순서에서 전체 조회/구독 등록을 묶고 클라이언트가 초기 상태 이후 이벤트를 순서대로 적용하는 정책을 정한다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| client/net/ConnectionState.java | 연결·인증·복구 단계 값 |
| client/net/SocketClient.java | 새 연결·오래된 작업 종료·상태 전달 |
| client/BoardController.java | 편집 중지·전체 교체·새 이벤트 적용 |
| server/service/BoardService.java | 재조회 시 권한·존재 확인 |
| server/session/BoardSubscriptions.java | 전환/끊김/로그아웃 구독 제거 |

새 연결 이후 도착한 옛 연결의 콜백은 무시할 식별자를 둔다. 현재 선택한 보드 ID와 다른 이벤트도 그대로 그리지 않는다.

## 5. 사람의 의도 → 실행 흐름

사용자는 끊김을 알아야 하고, 다시 들어오면 다른 사람이 만든 최신 결과를 볼 수 있어야 한다. 삭제된 보드에 계속 저장한다고 믿으면 안 된다.

```text
끊김 → 편집 중지·미승인 상태 안내 → 이전 작업/구독 정리
재연결 → 인증 → 보드 권한/존재 확인
최신 전체 조회와 새 구독의 순서 보장 → 모델 교체 → 준비 완료
삭제/접근 회수 → 서버 후속 요청 거절 → 클라이언트 편집 종료
미승인 요청 → 재전송 정책에 따라 확인; 성공으로 추정하지 않음
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

연결 상태를 구분하는 main 실습이다. 이 enum은 임시 클래스로 정의하고 GUI와 연결하기 전에 출력한다.

```java
enum State { DISCONNECTED, CONNECTING, AUTHENTICATING, LOADING, READY }

State state = State.LOADING;
boolean mayEdit = state == State.READY;
System.out.println(mayEdit);
```

출력은 false다. 소켓이 열려 있어도 최신 보드가 아직 준비되지 않았다. 실제 상태 전환과 UI 비활성화는 직접 연결한다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 각 상태의 안내 문구·허용 버튼을 정한다. '저장 실패'와 '저장 결과를 아직 모름'도 구분한다.
2. 끊기면 편집과 저장 성공 표시를 중지한다. 입력을 보존한다면 미승인 초안임을 표시한다.
3. 새 소켓에서 다시 인증하고 권한을 확인한다. 이전 연결의 세션이 살아 있다고 가정하지 않는다.
4. 전체 최신 모델로 교체하고 #41 이벤트와 초기 조회 사이 유실을 막는 순서를 구현한다.
5. 보드 A→B 전환, 로그아웃, 끊김마다 A 구독을 제거한다.
6. 삭제된 보드/권한 회수의 오류를 서버 읽기·쓰기 모두에서 반환한다. 화면의 편집을 끝내고 목록으로 안내한다.
7. 같은 요청의 재전송을 선택했다면 요청 ID별 결과 보존 범위·시간과 중복 처리 경계를 정한다. 없으면 자동 재전송하지 않는다.
8. 실제 보드 삭제 버튼은 #43의 저장 성공 조건을 연결한 뒤 완료 처리한다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| A 끊긴 동안 B 수정 후 A 재접속 | 최신 전체 상태 일치 | 단순 연결만 복구하는지 |
| 복구 중 B 연속 수정 | 마지막 변경까지 반영 | 조회·구독 사이 틈 |
| A 보드에서 B 보드로 전환 | 이전 보드 이벤트 없음 | 구독 제거 |
| 옛 수신 작업이 늦게 종료 | 새 연결 상태를 덮지 않음 | 연결 세대 식별 |
| 접속 중 보드 삭제 | 편집 종료, 후속 읽기/쓰기 거절 | 존재 검사 |
| 기록한 권한 회수 후 재접속 | 조회 거절 | 재인증 뒤 접근 재검사 |
| 저장 직후 응답 전 끊김 | 성공 단정/중복 생성 없음 | 미승인·중복 정책 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 재인증 후 전체 최신 상태를 복구한다.
- [ ] 초기 조회와 이벤트 사이 변경 유실을 시험한다.
- [ ] 이전 구독·작업이 남지 않는다.
- [ ] 삭제/접근 회수 뒤 읽기·쓰기 거절과 중복 요청 정책을 기록한다.
- [ ] 삭제 실행의 #43 연결이 남았다면 그 부분은 미완료로 표시한다.

리뷰 질문: 소켓 연결 성공인데도 편집을 막아야 하는 상태는? 전체 조회 후 구독하면 왜 틈이 생길까? 상태 전환·구독 정리·재조회 순서와 끊김 테스트를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
