## 1. 시작 상태와 이번 결과물

#37의 요청 전달과 #38의 사용자 저장 기반이 필요하다. 임시 작성자 대신 실제 로그인 사용자로 변경한다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

클라이언트가 '나는 사용자 A'라고 보낸 값만 믿으면 누구나 A를 사칭할 수 있다. 로그인은 계정 증명을 확인하는 과정, 세션은 확인한 사용자를 이후 연결/요청에 이어주는 서버 상태다.

비밀번호 해시는 복원이 아니라 비교를 위한 값이다. 일반 빠른 해시만 쓰거나 암호를 평문으로 저장하지 않고, 비밀번호 저장용 검증된 라이브러리를 사용한다.

로컬 학습용 평문 소켓을 인터넷 서비스로 공개하지 않는다. 외부 사용이 필요하면 TLS 등 전송 보호와 배포 범위를 먼저 검토한다. 로그에 암호나 인증 값을 출력하지 않는다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/service/AuthService.java | 가입·인증 규칙, 해시 API 연결 |
| server/store/UserRepository.java | 계정 식별자·해시 저장과 조회 |
| server/session/SessionRegistry.java | 연결 ID와 인증된 사용자 관계·제거 |
| client/ui/LoginView.java | 입력·처리 상태·일반 오류 표시 |
| server/ClientHandler.java | 연결 종료 시 세션 정리 |

로그인 화면이 성공 문구를 띄우는 것과 서버에 세션이 생성되는 것은 다른 단계다. 실패한 인증은 세션을 만들지 않는다.

## 5. 사람의 의도 → 실행 흐름

가입한 계정으로 들어와 자기 이름으로 카드를 만든다. 로그아웃했으면 열린 창이 남아 있어도 더 이상 그 계정으로 쓸 수 없다.

```text
가입: 입력 정책 검사 → 검증된 API로 비밀번호 해시 → 사용자 저장
로그인: 계정 조회 → API로 검증 → 성공한 연결에 사용자 매핑
쓰기: 연결의 세션 조회 → 없으면 거절 → 세션 사용자로 요청 처리
로그아웃/끊김: 세션 제거 → 구독 정리 → 이후 인증 필요
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

서비스 전체 인증 코드 대신 서버에서 세션의 존재 여부를 확인하는 독립 실습이다. 별도 scratch 패키지의 main 안에 넣고 import java.util.HashMap, java.util.Map을 추가한다. 운영용 SessionRegistry 구현은 직접 작성한다.

```java
Map<String, String> sessions = new HashMap<>();
sessions.put("connection-1", "user-A");
System.out.println(sessions.get("connection-1"));
sessions.remove("connection-1");
System.out.println(sessions.containsKey("connection-1"));
```

출력은 user-A와 false다. 키는 연결 식별자, 값은 서버가 인증한 사용자다. 이 예제는 로그인·해시·동시 접근을 구현하지 않는다. 실제 서버의 여러 작업이 공유하면 동시 접근 규칙이 필요하다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 중복 계정·공백·최대 길이·대소문자 정책을 기록한다.
2. 검증된 비밀번호 저장 API의 해시 생성·검증 최소 실습을 작성한다. 같은 암호의 해시값이 매번 같아야 한다고 가정하지 않는다.
3. 가입 후 DB에는 평문 대신 해시가 저장되는지 확인한다. 원문은 로그·오류·소켓 덤프에 남기지 않는다.
4. 계정 중복은 UI 확인뿐 아니라 DB의 유일성 제약과 서버 오류 처리로 막는다.
5. 로그인 성공 시 서버 연결에 사용자 ID를 연결한다. 실패 시 일반화된 인증 실패 문구를 정한다.
6. 카드 요청의 작성자 값을 조작해도 서버 세션 사용자로 처리되는지 확인한다.
7. 로그아웃/끊김에 세션과 보드 구독을 제거하고 클라이언트의 계정별 데이터를 비운다. 캐시 정리는 #45에서 연결한다.
8. 소유/참가 권한은 #40에 맡기고 인증 코드에 보드 SQL을 섞지 않는다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| A·B 가입과 로그인 | 서로 다른 서버 사용자 | 세션 매핑 |
| 같은 계정 동시 가입 | 하나만 생성 | DB 유일성 제약 |
| 틀린 암호·없는 계정 | 세션 없음·일반 실패 | 실패 경로 |
| 로그인 없이 쓰기 | 거절 | 요청 입구 검사 |
| A 연결에서 authorId=B 전송 | B 사칭 불가 | 클라이언트 값 신뢰 여부 |
| 로그아웃 후 쓰기 재전송 | 거절 | 세션 삭제 |
| 연결 끊고 다시 연결 | 이전 인증 자동 승계 없음 | 끊김 정리 |
| DB·로그 확인 | 평문 암호 없음 | 디버그 출력 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 가입·로그인·로그아웃과 두 계정을 확인한다.
- [ ] 해시 라이브러리 선택과 입력 정책을 기록한다.
- [ ] 요청 주체는 서버 세션에서 정한다.
- [ ] 로그아웃·끊김 후 쓰기 거절과 민감정보 미출력 증거를 남긴다.

리뷰 질문: 화면의 userId와 서버 세션 중 무엇을 믿는가? 해시와 암호화는 무엇이 다른가? 암호값을 제외한 AuthService·세션 처리·테스트 결과를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
