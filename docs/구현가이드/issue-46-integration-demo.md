## 1. 시작 상태와 이번 결과물

#42~#45까지 연결되었거나 남은 실패가 명확히 기록된 상태에서 시작한다. 안내서가 있다는 이유로 구현 완료로 표시하지 않는다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

각 기능을 따로 성공시킨 것과 전체 흐름이 성공하는 것은 다르다. 예를 들어 저장은 성공했지만 재접속이나 비공개 전환 뒤 이전 화면이 남을 수 있다.

검증은 입력·기대 결과·실제 결과를 비교하는 작업이다. 스크린샷만 찍기보다 어떤 계정·보드·버전·동작으로 결과를 만들었는지 기록해야 재현할 수 있다.

## 3. 지금 정할 것과 미룰 것

- 지금: 두 계정·두 클라이언트·두 보드, 분리된 테스트 DB와 이미지 폴더.
- 결정 필요: 교수자의 실행/제출 요구와 JavaFX 사용 허용. 개발 실행 안내와 배포 실행 안내를 구분한다.
- 나중: 설치 파일이 요구되면 별도 패키징 작업으로 계획한다.
- 제외: 검증하지 않은 100명 동시 접속 성능 주장·유료 배포 서비스.

새 폴더에서 실행하되 기존 사용자 DB/파일을 지우지 않는다. Maven/JDK·초기 인터넷 요구가 있는 개발 방식과 별도 JDK 없는 설치형 배포는 다르다.

## 4. 파일별 책임과 연결

| 결과물 또는 제안 파일 | 맡길 일 |
|---|---|
| app의 설정 파일 | 주소·포트·DB·이미지 경로, 비밀 없는 예시 |
| 개발 실행 안내 | JDK·Maven Wrapper·서버/클라이언트 순서·두 실행 방법 |
| 본인 작성 검증 기록 | V 항목별 조건·실제 결과·증거·관련 결함 |
| 본인 작성 시연 순서 | 준비 데이터·5분 흐름·실패 시 안내 |
| 본인 작성 회고 | 파일 역할·학습한 기술·남은 한계 |

제출 보고서 전체는 이 문서로 대신하지 않는다. 본인이 구현한 코드와 실제 결과로 최종 설명을 작성한다.

## 5. 사람의 의도 → 실행 흐름

처음 보는 사람도 안내대로 실행할 수 있고, 실제 사용자가 글·이미지를 붙여 함께 정리하고 결과를 보관하는 이유를 알 수 있게 보여준다.

```text
독립 테스트 폴더 준비 → 버전/설정 확인 → DB·이미지 경로 분리
서버 시작 → 두 클라이언트 로그인 → V 항목 순서대로 실행
기대와 실제 비교 → 실패는 결함 기록 → 수정 후 재검증
시연 데이터 준비 → 300초 리허설 → 실제 시간 기록
파일 책임과 수업 기술을 자기 말로 설명 → 완료/미완료 표시
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

기능 코드 대신 시연 시간을 재는 독립 main 실습이다. 사용자 흐름을 실행하는 동안에는 휴대폰 타이머 등을 사용해도 된다.

```java
long start = System.nanoTime();
System.out.println("시연 시작 — 종료할 때 Enter");
new java.util.Scanner(System.in).nextLine();
double seconds = (System.nanoTime() - start) / 1_000_000_000.0;
System.out.println("걸린 시간: " + seconds + "초");
```

nanoTime 차이는 경과 시간을 측정한다. 이 출력은 기능 통과 증거가 아니며, 실제 시연에서 전체 흐름을 함께 측정해야 한다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. JDK·JavaFX·드라이버·빌드 도구 버전과 실행 명령을 실제 값으로 정리한다.
2. 새 테스트 폴더에 필요한 코드/설정만 준비한다. 누락된 이미지 경로·DB 초기화·포트 사용을 확인한다.
3. 서버를 먼저 실행하고 두 클라이언트를 연다. 주소·포트가 다른 경우 안내를 확인한다.
4. 아래 검증표를 본인의 결과 기록으로 복사해 실제 결과를 채운다. 실패를 빈칸이나 성공으로 숨기지 않는다.
5. 경계·권한·충돌·실패를 수정한 뒤 동일 조건으로 다시 재현한다.
6. 시연 계정·작은 이미지·두 보드를 준비한다. 가입/대용량 다운로드로 시간을 소비할지 의도적으로 정한다.
7. 아래 5분 예시 순서를 직접 조정해 리허설하고 실제 시간을 남긴다.
8. 저장소에 비밀번호·세션·실제 사용자 DB·개인 파일이 포함되지 않았는지 확인한다.
9. 핵심 함수의 입력→검사→저장→통보→화면 흐름을 자기 말로 설명하고 남은 제한을 적는다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

### 5분 시연 초안 — 리허설로 조정

| 구간 | 보여줄 사용자 행동 | 연결 기술 |
|---|---|---|
| 0:00~0:40 | 로그인·보드 입장 | 인증·서버 세션 |
| 0:40~1:40 | 글·이미지 추가·수정 | 이벤트·이미지 처리 |
| 1:40~2:40 | 이동·두 화면 반영·충돌 예시 | 소켓·스레드·버전 |
| 2:40~3:20 | 보드 재조회·저장 확인 | JDBC |
| 3:20~4:20 | 삭제 전 스냅샷·보관함 | 일관된 이미지·저장 실패 순서 |
| 4:20~5:00 | 공개 갤러리·썸네일 재조회 카운터 | 권한·캐시 |

환경 설치까지 5분이라는 뜻은 아니다. 준비된 실행 환경에서 참여·사용 흐름을 시연한다. 시간표는 목표이며 실제 측정 전 성공으로 주장하지 않는다.

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] V-01~V-14마다 실제 판정·증거·결함/재검증 결과가 있다.
- [ ] 새 폴더에서 안내만으로 실행하고 필요한 환경을 명시한다.
- [ ] 실제 시연을 300초 안에 마치고 시간을 기록한다.
- [ ] 직접 쓴 핵심 코드의 책임과 기술 사용 이유를 설명한다.
- [ ] 미완료·검증하지 않은 부분을 분명히 밝힌다.

리뷰 질문: 서버가 승인한 변경만 성공으로 보이는가? 시연에 없던 실패 테스트는 어디에 기록됐는가? 실행 안내·검증 기록·실제 시연 시간·직접 쓴 코드 설명을 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
