# #43 · 보드 스냅샷·삭제 전 보관

최종 보드의 글·이미지·좌표·겹침을 이미지로 보관한다. 저장 실패 시 보드는 남고, 재시작 후 내 스냅샷을 다시 연다.

## 1. 시작 상태와 이번 결과물

#36·#38·#40~#42의 이미지·저장·권한·동기화·삭제 통보가 필요하다. 실제 삭제는 이번 단계의 보관 성공 뒤에만 허용한다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

스냅샷은 특정 시점의 모습을 고정해 보관하는 이미지다. 화면에 보이는 일부만 캡처하거나 삭제 직전 들어온 변경을 놓치면 최종 보드의 기록이 아니다.

DB와 이미지 파일은 서로 다른 저장 장소다. DB rollback만으로 이미 쓴 파일을 지울 수 없으므로 임시 파일·확정·정리 절차가 필요하다.

## 3. 지금 정할 것과 미룰 것

- 지금: 보드 크기·카드 모양·줄바꿈 규칙을 정하고 서버의 카드 값이 최종 기준이 되게 한다.
- 최소 실습: 클라이언트 화면 snapshot으로 한 장을 얻어 본다. 최종 보관의 신뢰 근거로는 부족하다.
- 결정 필요: 서버 렌더링 방식. Java2D BufferedImage는 JavaFX 화면을 띄우지 않고 그릴 수 있지만 카드 모양을 별도로 맞춰야 한다. 서버 JavaFX는 초기화·화면 스레드 조건과 배포 환경을 검토해야 한다.
- 나중: PDF·고해상도·여러 파일 형식.

삭제 처리 중 편집을 어떻게 막을지 정한다. 단일 서버에서는 해당 보드 변경을 잠시 보호하고 동일 상태로 렌더링/저장/삭제하는 방식부터 검토한다. 렌더링 실패로 보호가 영구 남지 않도록 해제 경로를 둔다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/image/SnapshotRenderer.java | 일관된 카드 목록→전체 보드 이미지, z순서·줄바꿈 |
| server/service/SnapshotService.java | 소유자·보드 상태·보관과 삭제의 순서 |
| server/store/SnapshotRepository.java | 소유자·이미지 ID·버전·비공개 상태 저장 |
| server/store/ImageStore.java | 임시 파일·확정 경로·실패 정리 |
| client/ui/SnapshotListView.java | 내 목록·상세 표시 |

SnapshotRenderer는 사용자를 인증하지 않는다. SnapshotService가 검증한 데이터만 전달한다. 스냅샷은 보드 삭제 뒤에도 독립적으로 남아야 한다.

## 5. 사람의 의도 → 실행 흐름

사용자가 보드를 지워도 결과는 보관함에 남는다. 보관할 수 없으면 삭제하지 않았다는 안내를 받는다.

```text
삭제 요청 → 소유자·보드 존재 확인 → 보드 변경 보호
서버 최신 카드 목록 확보 → 순서대로 전체 이미지 렌더링
임시 이미지 저장 → 스냅샷 기록·보드 삭제를 안전한 순서로 확정
성공 → 삭제 통보·보관함 갱신
실패 → DB 취소·파일 보상·보드 유지 → 보호 해제·실패 안내
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

#34의 board Pane이 Scene에 연결된 상태에서 버튼 이벤트 안에 넣는 캡처 관찰 예제다. import javafx.scene.image.WritableImage를 추가한다. 호출은 JavaFX 화면 스레드에서 한다.

```java
WritableImage captured = board.snapshot(null, null);
System.out.println(captured.getWidth() + " x " + captured.getHeight());
```

snapshot은 현재 Node의 모습을 이미지로 돌려준다. 파일 저장·서버 최종 상태·보드 삭제는 하지 않는다. 컨테이너가 스크롤로 잘리거나 크기가 다르면 전체 보드 보존과 다를 수 있다. 최종 렌더링은 서버 모델 기준으로 직접 구현한다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 캡처 실습에서 보드 크기와 이미지 크기를 비교한다. 글·이미지·겹침을 준비한다.
2. 서버 렌더링 방식을 선택하고 한 카드→두 카드→이미지 포함 순서로 작은 비교 실습을 만든다.
3. 모델 순서대로 전체 보드를 그린다. 한글 폰트·줄바꿈·비율·경계가 화면과 의도대로 같은지 확인한다.
4. 스냅샷 기본 비공개와 소유자·버전을 저장한다. 삭제될 보드 FK가 결과를 함께 지우지 않게 한다.
5. 삭제 중 편집 정책과 보호 범위를 정한다. 최신 상태 확보~삭제 완료 사이에 들어온 요청 처리도 기록한다.
6. 임시 파일 확정과 DB commit 순서를 직접 설계한다. 실패 지점을 목록으로 만든다.
7. 모든 필수 보관이 완료된 뒤 보드를 삭제한다. 저장 실패는 삭제 통보를 보내지 않는다.
8. 서버가 중간에 종료된 경우의 잔여 파일/처리 중 상태를 확인·복구할 절차를 정한다.
9. 내 스냅샷 목록과 이미지 상세 조회를 연결하고 서버 재시작 후 확인한다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| 글·한글·이미지·겹침 보드 삭제 | 최종 배치 이미지와 보관함 | 렌더 순서·폰트·크기 |
| 소유자 아닌 사용자의 삭제 | 거절, 보드 유지 | 서버 소유 검사 |
| 이미지 쓰기 실패 | 보드 유지, 실패 안내 | 삭제 순서 |
| 파일 성공 뒤 DB 실패 | 보드 유지, 잔여 정리 | 보상 작업 |
| 보관 도중 다른 사용자가 수정 | 정한 일관성 정책, 기록 누락 없음 | 보호 경계 |
| 보관 도중 서버 종료·재시작 | 손실 없이 기록한 복구 절차 | 임시/확정 구분 |
| 서버 재시작 후 내 목록·이미지 | 보관 결과 재조회 | 경로·FK·소유자 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 서버 기준 최종 보드 이미지가 보존된다.
- [ ] 보관 실패 시 보드를 삭제하지 않는다.
- [ ] 동시 편집·DB/파일 부분 실패·중간 종료 정책을 기록한다.
- [ ] 재시작 뒤 내 목록·이미지 조회가 가능하다.
- [ ] #42의 삭제 실행과 통보를 최종 보관 순서에 연결한다.

리뷰 질문: 내 화면 캡처를 그대로 믿으면 다른 사용자의 최신 수정이 빠질 수 있는가? 파일 확정 뒤 DB 실패면 무엇을 해야 하는가? 렌더 비교·삭제 순서·실패 지점 테스트를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
