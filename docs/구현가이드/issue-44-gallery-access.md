# #44 · 스냅샷 공개 갤러리·삭제

소유자가 공개/비공개/삭제한다. 다른 사용자는 공개 결과만 볼 수 있고 공개 해제 뒤 새 상세·이미지 요청은 거절된다.

상태: 학습·구현 안내서. 아래 동작은 완료 목표이며 현재 구현됐다는 뜻이 아니다.

## 1. 시작 상태와 이번 결과물

#43의 보존된 스냅샷과 소유자 목록이 필요하다. 보드 참가자여도 스냅샷 공개를 관리할 권한은 자동으로 생기지 않는다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

목록에 안 보이게 하는 것만으로 비공개가 되지 않는다. ID를 알아 이미지 요청을 직접 보내면 열릴 수 있으므로 목록·상세·이미지 모두 서버의 같은 권한 규칙을 따라야 한다.

메타데이터 버전은 공개 상태 같은 정보가 바뀌었음을 구분한다. 원본 그림이 같아도 공개 상태가 바뀌면 캐시가 최신 권한을 다시 확인해야 한다.

## 3. 지금 정할 것과 미룰 것

- 지금: 기본 비공개, 소유자 관리, 공개 결과를 감상하는 갤러리.
- 결정 필요: 갤러리 로그인 필요 여부·페이지 크기·삭제 파일 정리 재시도 정책.
- 나중: #45의 썸네일 캐시와 무효화 연결.
- 제외: 공개된 스냅샷으로 원본 보드 편집 권한 부여.

이미 다운로드한 사본을 회수할 수는 없다. 공개 해제는 이후 서버 요청을 막는 기능으로 설명한다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/service/SnapshotService.java | 읽기·공개 전환·삭제의 통합 권한 |
| server/store/SnapshotRepository.java | 공개 목록·소유 목록·버전 변경 |
| server/store/ImageStore.java | 삭제 파일·잔여 정리 재시도 |
| client/ui/SnapshotGalleryView.java | 공개 목록·상세·관리 버튼 |
| protocol/Message.java | 공개/비공개/삭제 결과와 변경 버전 |

이미지 저장 디렉터리를 권한 검사 없이 외부에 노출하지 않는다. 이미지 ID 요청도 SnapshotService를 거쳐 실제 소유/공개 상태를 확인한다.

## 5. 사람의 의도 → 실행 흐름

사용자는 자기 작품을 공개했다가 다시 숨길 수 있다. 다른 사용자는 남의 공개 상태를 바꾸거나 비공개 이미지를 꺼낼 수 없어야 한다.

```text
읽기 요청 → 스냅샷 존재 확인 → 소유자 또는 공개 정책 검사
목록/상세/원본/썸네일 모두 같은 규칙 적용
공개 전환 → 소유자 확인 → 버전 증가 저장 → 갱신 결과
삭제 → 소유자 확인 → 논리 접근 차단/DB 변경 → 파일 정리
파일 정리 실패 → 재시도 기록; 조회 가능 상태로 되돌리지 않음
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

공개 여부의 조건만 확인하는 독립 main 실습이다. 실제 서비스의 인증·DB 조회·삭제 판정은 직접 작성한다.

```java
boolean isOwner = false;
boolean isPublic = true;
boolean mayRead = isOwner || isPublic;
boolean mayChangeVisibility = isOwner;
System.out.println(mayRead + " / " + mayChangeVisibility);
```

결과는 true / false다. 볼 수 있다고 공개 상태를 관리할 수 있는 것은 아니다. 실제 읽기는 스냅샷 존재와 서비스의 로그인 정책도 먼저 검사한다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 소유자 A와 비소유자 B를 준비한다. 기본 비공개 생성 결과를 확인한다.
2. 소유 목록·공개 목록·상세·원본 이미지·썸네일 요청 경로를 종이에 모두 적는다.
3. 각 경로에서 같은 권한 정책을 호출한다. 클라이언트 버튼 노출은 별도 편의 처리다.
4. 소유자만 공개 상태를 바꾸게 한다. 변경은 서버 메타데이터 버전에 반영한다.
5. B가 이미 알고 있는 ID로 비공개 전환 뒤 다시 요청해 거절을 확인한다.
6. 삭제 요청은 읽기 차단과 파일 정리를 구분한다. 정리 실패 시 재시도할 정보를 저장한다.
7. 갤러리를 새로고침하고 열린 상세 화면의 상태를 갱신한다. 캐시 정리는 #45에 연결한다.
8. 공개 해제/삭제가 이후 요청에 즉시 반영되는지 확인한다. 이미 받은 사본 회수는 약속하지 않는다.

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| 새 비공개 스냅샷을 B가 목록/ID로 조회 | 목록 제외·상세/이미지 거절 | 목록만 필터한지 |
| A가 공개 후 B 조회 | 정책에 맞게 표시 | 공개 저장·갱신 |
| B가 공개 변경/삭제 요청 | 거절 | 읽기와 관리 권한 혼동 |
| A 비공개 전환 뒤 B 직접 이미지 요청 | 새 요청 거절 | 파일 경로 우회 |
| A 삭제 후 ID 재요청 | 없음/거절, 목록 제외 | 원본·썸네일 각각 검사 |
| 파일 삭제 실패 | 접근은 차단, 정리 재시도 기록 | DB와 파일 순서 |
| 공개 상태 변경 | 버전 증가, 오래된 상태 무효 | 메타데이터 버전 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 기본 비공개와 소유자 관리가 서버에 적용된다.
- [ ] 목록·상세·원본·썸네일 모두 권한 검사를 통과한다.
- [ ] 공개 해제·삭제 후 직접 이미지 재요청도 막는다.
- [ ] 버전 변경과 파일 정리 실패 처리를 기록한다.

리뷰 질문: 목록에서는 숨겼지만 이미지 파일이 열린다면 어디가 빠졌는가? 보드 참가자와 스냅샷 소유자는 같은가? 전체 접근 경로·권한 코드·다른 계정 테스트를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
