# #40 · 보드 관리·공유 코드·편집 권한

보드를 만들고 공유 코드로 참여한다. 소유자는 전체 카드를, 참가자는 자기 카드만 관리하고 이전 코드는 새 참여에 쓸 수 없다.

상태: 학습·구현 안내서. 아래 동작은 완료 목표이며 현재 구현됐다는 뜻이 아니다.

PRD 연결: B-02, B-03, B-06, V-01, V-03, V-04 — [기준 문서](../기말프로젝트_PRD.md)

## 1. 시작 상태와 이번 결과물

#38의 DB 저장과 #39의 인증된 요청자를 사용한다. 보드 목록과 참가 관계를 직접 만든다.

이 문서의 파일은 app/src/main/java 아래 패키지 경로 기준의 제안이다. 이미 파일이 있다면 먼저 읽고 재사용한다. 이 안내서가 실제 파일이나 기능을 만들어 놓은 것은 아니다.

이번 결과물은 직접 작성한 코드, 실행 순서, 아래 테스트의 실제 결과, 선택한 정책과 짧은 회고다. 선행 단계가 실패하면 먼저 그 문제를 해결한다.

## 2. 먼저 이해할 개념

인증은 누구인지, 권한은 그 사람이 무엇을 해도 되는지다. 버튼을 숨겨도 통신 요청을 직접 보내면 우회될 수 있으므로 서버가 모든 요청을 검사해야 한다.

공유 코드는 참여 수단이고 보드 ID는 내부 대상 식별자다. 코드 변경과 기존 참가 관계 삭제는 같은 동작이 아니다.

## 3. 지금 정할 것과 미룰 것

- 지금: 보드 소유자·참가 관계·카드 작성자를 기준으로 권한을 정한다.
- 결정 필요: 코드 변경 후 기존 참가자를 유지할지 회수할지, 코드 길이/중복/추측 방지 정책.
- 나중: 회수 통보·재접속은 #42, 스냅샷 공개는 #44.
- 제외: 스냅샷 공개를 보드 전체 편집 공개로 간주하기.

내 보드 목록에 소유 보드만 넣을지 참여 보드도 넣을지 선택하고 화면에서 구분한다. 코드 변경은 이전 코드로 신규 참여를 막아야 한다.

## 4. 파일별 책임과 연결

| 제안 파일 | 맡길 일 |
|---|---|
| server/service/BoardService.java | 생성·참여·조회·제목/코드 변경 규칙 |
| server/service/PermissionPolicy.java | 요청별 권한 판정; DB 값·세션 사용 |
| server/store/BoardRepository.java | 보드·참가 관계·공유 코드 저장 |
| client/ui/BoardListView.java | 내 보드·참여 입력·생성 화면 |
| server/service/NoteService.java | 편집마다 권한 정책을 호출 |

권한 판정용 작성자·소유자 값은 서버 DB에서 가져온다. 클라이언트가 보낸 isOwner=true 같은 값을 신뢰하지 않는다.

## 5. 사람의 의도 → 실행 흐름

남의 카드는 볼 수 있어도 마음대로 고칠 수 없다. 보드 주인은 전체 정리와 제목·초대 코드 관리를 할 수 있다.

```text
요청 → 세션 사용자 확인 → 보드 존재 확인 → 접근/참가 확인
보드 관리 → 소유자이면 진행, 아니면 거절
카드 변경 → 이 보드 카드인지 확인 → 작성자/소유자이면 진행
공유 코드 변경 → 소유자 확인 → 새 코드 저장 → 이전 신규 참여 거절
기존 참가자 처리 → 선택한 정책 적용·기록
```

위 순서를 자신의 말로 먼저 설명한다. 다음 예제로 API 하나를 확인한 뒤 서비스 흐름은 직접 작성한다.

## 6. 아주 작은 예제와 읽는 법

UI 없이 조건식의 의미만 확인하는 main 실습이다. 실제 판정은 DB에서 읽은 관계로 직접 작성해야 한다.

```java
String actor = "user-B";
String author = "user-A";
String owner = "user-C";
boolean participant = true;
boolean mayEdit = participant
    && (actor.equals(author) || actor.equals(owner));
System.out.println(mayEdit);
```

결과는 false다. 참가했다고 타인 카드를 편집할 수 있는 것은 아니다. 소유자를 접근 가능한 사용자로 포함하는 규칙도 실제 정책에 넣는다. 이 예제에는 존재 확인·실제 DB·인증이 없다.

이 예제의 생략한 책임을 확인한다. 예제가 실행된 것과 이슈의 기능이 완성된 것은 다르다. 동작하는 예제에 한 기능씩 더하고 확인한다.

## 7. 직접 구현하는 순서

1. 아래 권한표를 본인의 정책과 대조하고 참가자 유지/회수 결정을 기록한다.
2. 보드 생성·내 목록·ID 조회를 서버와 연결한다. ID를 알았다는 이유만으로 접근을 허용하지 않는다.
3. 공유 코드로 참여하면 중복 참가를 만들지 않도록 저장한다.
4. 제목·코드 변경은 소유자만 승인한다. 새 코드는 충돌하지 않게 생성·저장한다.
5. 카드 생성·수정·이동·삭제마다 세션과 보드 접근·작성자 규칙을 적용한다.
6. UI 비활성화와 별도로, 비허용 사용자의 실제 요청을 보내 서버 거절을 확인한다.
7. 미정 정책을 결정했으면 PRD와 이슈에 근거·선택·테스트를 맞춰 적는다.

| 요청 | 소유자 | 일반 참가자 | 미참가자 |
|---|---|---|---|
| 보드 조회·카드 생성 | 허용 | 허용 | 거절 |
| 자기 카드 수정·이동·삭제 | 허용 | 허용 | 거절 |
| 다른 사람 카드 변경 | 허용 | 거절 | 거절 |
| 제목·코드 변경 | 허용 | 거절 | 거절 |

각 단계가 끝날 때 기대한 동작이 실제로 되는지 확인한다. 실패하면 첫 오류와 재현 입력을 남기고 다음 단계로 넘어가지 않는다.

## 8. 예외·경계값 테스트

| 재현 방법 | 기대 결과 | 어긋날 때 확인 |
|---|---|---|
| A 소유 보드에 B 코드 참여 | 참가 관계 저장 | 코드 조회·중복 처리 |
| B가 A 카드 이동·삭제 요청 | 거절, 데이터 유지 | 모든 편집 경로의 권한 |
| A가 B 카드 변경 | 허용 | 소유자 규칙 |
| 미참가 C가 보드 ID 추측 | 조회·쓰기 거절 | 읽기 권한 검사 |
| 코드 변경 후 이전 코드 사용 | 신규 참여 거절 | 이전 매핑 제거 |
| 기존 B가 코드 변경 뒤 요청 | 기록한 유지/회수 정책과 일치 | 참가 관계 처리 |
| 다른 보드의 카드 ID 전달 | 대상 불일치 거절 | 카드의 boardId 검사 |

### 실제 결과 기록

```text
코드 버전 / 실행 환경:
검사 항목:
준비한 계정·보드·데이터:
내가 한 행동:
기대 결과:
실제 결과: 미실행 / 통과 / 실패
증거와 오류:
원인·수정:
같은 조건 재검증:
```

검사표는 기대 결과다. 실제로 실행하기 전에는 체크하지 않는다. 개인 암호·세션·민감한 경로는 증거에서 제외한다.

## 9. 리팩터링·회고·완료 기준

동작을 확인한 뒤 긴 이벤트에서 계산·검사·저장 책임을 분리한다. 처음부터 제안된 모든 클래스를 빈 파일로 만드는 데 시간을 쓰지 않는다.

- [ ] 생성·목록·참여·제목/코드 변경이 저장된다.
- [ ] 서버가 소유자·작성자·참가 여부를 검사한다.
- [ ] 이전 코드 신규 참여와 타인 카드 편집을 차단한다.
- [ ] 기존 참가자 정책과 권한표 테스트를 기록한다.

리뷰 질문: 로그인했는데도 거절해야 하는 요청은 무엇인가? 공유 코드 변경이 왜 권한 회수와 같지 않은가? 서버 권한 함수와 실제 거절 요청 결과를 리뷰받는다.

완료 보고에는 바꾼 파일, 확인한 테스트, 아직 남은 실패/미정, 다음 단계에 넘길 데이터와 규칙을 적는다. 핵심 구현과 제출 설명은 직접 작성하고 AI에는 개념·힌트·작은 예제·내 코드 리뷰를 요청한다.
